广告点击聚合器设计 ​

广告点击聚合系统是一个兼具高并发在线请求处理与实时分析计算特征的典型架构设计场景。整个链路涵盖了点击跳转控制、事件采集、流式聚合计算、高吞吐写入、低延迟查询、热点数据分片、系统可靠性保障以及点击防伪与校验等多个核心工程难点

问题定义与需求 ​

问题定义 ​

系统的核心职责主要分为两部分：当用户点击广告时，系统必须迅速且正确地将用户重定向至广告主的落地页；同时，系统需要准确无误地采集该次点击事件，并支持广告主按自定义时间范围对广告的点击指标进行多维度查询。

  • 功能需求

用户点击广告后，可以被正确跳转到广告主目标页面；广告方能够查询特定广告在指定时间窗口内的点击流量；查询结果至少支持分钟级别的聚合

  • 规模假设

峰值写入压力约为 10k clicks/s；以分钟级的时序聚合指标查询为主；广告方希望尽可能接近实时地看到点击变化

  • 非功能需求
  1. 可扩展性：能够稳定支撑高频点击写入
  2. 低延迟：广告方查询不能过慢
  3. 可靠性：不能丢失点击数据
  4. 正确性：需要处理重复点击和伪造点击

核心实体 ​

  • Click Event
  • Ad
  • Advertiser
  • Impression ID
  • Aggregated Metrics

系统接口与数据流 ​

系统接口 ​

  • 写路径输入：接收来自客户端的广告点击请求
  • 写路径输出：完成事件记录后，返回目标页面的重定向响应
  • 读路径输入：接收广告方包含广告 ID 与时间范围的查询请求
  • 读路径输出：返回按分钟粒度计算好的点击指标时间序列

数据流 ​

  1. 广告在客户端完成展示时，投放系统预先生成一个全局唯一的 impression id
  2. 用户发生点击行为，请求携带相关参数进入后端的点击处理服务
  3. 点击处理服务首先对请求的合法性（如签名防伪）进行严格校验
  4. 校验通过的合法点击事件，作为消息载荷被追加写入高性能事件流（如 Kafka/Kinesis）
  5. 流计算引擎（如 Flink/Spark Streaming）作为下游消费者，持续订阅点击事件并执行时间窗口聚合
  6. 完成窗口计算的聚合结果，被批量写入专为多维查询优化的分析型数据库（OLAP）
  7. 广告主发起业务查询时，后端系统直接命中 OLAP 库中的预聚合数据，快速组装并返回分钟级指标

由此可见，该系统天然划分为两条边界清晰的链路：一条是面向 C 端用户的在线点击采集与跳转链路，另一条是面向 B 端广告方的异步聚合与分析查询链路

核心架构设计 ​

点击链路的跳转策略设计 ​

最直观的跳转实现是在前端直接发起页面路由，同时异步请求后端 /click 接口进行埋点上报。这种客户端直连方案虽然实现成本极低，但存在致命缺陷：用户或脚本可以轻易绕过埋点逻辑直接访问落地页，或者因网络波动导致异步上报失败，最终造成点击数据的严重漏报

为了保障数据采集的完整，更合理的方式是采用服务端重定向

  1. 用户点击广告后，请求需要先进入我们的点击处理服务
  2. 服务端在内存或异步日志中完成点击事件的记录
  3. 随后服务端返回 302 Redirect，由浏览器接管并跳转至最终的广告主页面

这样做的优势是，点击上报与实际跳转被耦合在同一条 HTTP 请求链路中，只要发生了有效跳转，就必然会经过采集服务。与此同时，点击处理服务通常要求在几十毫秒内返回 302 响应，以避免用户感知到明显的跳转卡顿

存储选型与查询架构 ​

如果采用最原始的单体架构思路，系统会将所有原始点击事件直接 INSERT 写入关系型数据库，并在查询时通过大范围的 GROUP BY 执行现场聚合。在面临 10k clicks/s 的写入规模时，这种方案会导致数据库同时承受海量的行级并发写入与极其消耗 CPU 的全表聚合扫描，读写资源的剧烈争抢将迅速压垮数据库实例

为了解决资源争抢问题，系统需要进行读写分离与架构解耦，引入独立的分析型存储系统

  • 系统先将原始事件落盘，随后通过定时任务（如每分钟触发一次 Cron Job）对增量数据进行批处理聚合，并将结果回写至 OLAP 数据库

这种模式缓解了读写冲突，但查询结果的可见性会受限于批处理周期的延迟（至少延迟一分钟以上），那么为了进一步降低延迟，系统可以引入流式处理计算

  • Click Processor 将原始请求作为无状态事件投入消息队列（Kafka/Kinesis）。后端的 Flink 或 Spark 节点持续摄取事件流，基于事件时间（Event Time）进行滚动或滑动窗口聚合。聚合产生的高密度指标数据随后被推入 ClickHouse、Druid 等 OLAP 引擎

这样一来，系统就从“周期性批处理”升级为“持续增量处理”，既能保证较高写入吞吐，也能把查询延迟压到较低水平

深入讨论 ​

一、如何扩展到 10k clicks/s ​

广告点击聚合系统本质上是一个写密集型系统。Click Processor 层相对容易扩展，只要服务是无状态的，就可以通过负载均衡和水平扩容来承载更多请求

  • 分区键

难点在于流计算与状态聚合层。在流处理架构中，最直观且常用的分片键（Partition Key）通常是 AdId（广告 ID）。基于广告 ID 进行哈希路由，能够确保同一广告的所有点击事件被稳定分发至同一个消息分区（Partition），从而极大简化 Flink 算子内部的状态管理与聚合逻辑

但这个策略会带来典型的热点分片问题。某些热门广告可能在短时间内吸引远高于平均值的点击量，导致所有流量集中进入单个分区，形成 hot shard。一旦某个分区负载过高，不仅处理延迟会升高，严重时还可能引发消费积压甚至数据丢失风险

  • 细分热点广告的分区键

例如，将原始 AdId 扩展成 AdId:0-N，通过附加随机后缀把高并发点击分散到多个 shard 中。随后在 Flink 聚合完成、写入 OLAP 之前，再把这个后缀去掉，按原始广告 ID 汇总结果。这样可以在不改变查询模型的前提下，显著缓解热点问题

对于流处理层，通常可以让多个任务并行消费不同的 Kafka 或 Kinesis 分区，各自维护局部聚合状态，再把结果写入分析库。至于 OLAP 数据库，如果采用托管型产品如 Snowflake 或 BigQuery，扩展通常交由平台处理；如果采用自建方案如 ClickHouse，则需要根据查询模式进一步设计分片方式，例如按广告主或查询热点维度分布数据

二、如何保证不丢失点击数据 ​

在可靠性设计上，流系统承担的是非常关键的角色。Kafka 和 Kinesis 并不只是消息传输通道，它们同时也是系统的短期可恢复事件缓冲层。只要配置了副本与保留周期，点击事件就不会因为下游处理器的短时故障而直接丢失

例如，如果流系统保留原始点击事件 7 天，那么即使 Flink 在某一时刻故障，恢复之后仍可以从流中重新消费故障期间未处理的历史事件。相比之下，聚合结果的重复计算通常是可接受的，而点击事件一旦丢失，就往往无法补回。因此，系统必须优先保证点击原始事件的完整性

从这个角度看，Kafka 或 Kinesis 不只是系统的异步解耦层，更是整个系统的可靠性基石

三、如何处理重复点击与伪造点击 ​

广告点击系统还必须考虑如何区分真实点击、重复点击和伪造点击

到这里系统需要引入 impression id 的概念。广告被展示给用户时，广告投放服务会为每次展示生成一个唯一的 impression id，并对其进行签名，然后一并返回给前端。用户点击广告时，会把这个带签名的 impression id 与点击请求一起提交回来

点击处理服务拿到请求后的处理顺序通常如下

  1. 验证 impression id 的签名，确保请求确实对应一次真实展示，而不是客户端伪造
  2. 检查缓存中是否已经见过这个 impression id
  3. 如果见过，则说明这是重复点击，可以忽略
  4. 如果没见过，则先把点击写入流系统，再把该 impression id 写入缓存，用于后续去重

这里最重要的点在于写入顺序必须是先写流，再写缓存。如果先写缓存、后写流，而流写入失败，那么这条点击就会被错误地标记为已处理，从而造成永久性数据丢失；反过来，如果先写流、后写缓存，即使缓存写入失败，最坏的结果也只是放进来少量重复点击，后续仍可通过对账或补偿逻辑修正

四、为什么不能直接查原始事件 ​

这往往是分布式系统设计中最容易陷入的误区。在低并发场景下，直接查底表是常态。但在广告计费这种吞吐级别的系统中，将在线采集（OLTP）与分析查询（OLAP）揉杂在同一张数据库原始明细表中，是引发系统崩溃的直接原因

只有将数据流彻底切分，系统才能做到：

  • 写路径持续高吞吐
  • 聚合链路可独立扩展
  • 广告主查询延迟可控
  • 原始事件与分析结果职责清晰

总结 ​

一个成熟的广告点击聚合系统，可以沿着下面七种维度逐步构建：

  1. 采用服务端重定向，确保点击路径完整
  2. 用 Kafka 或 Kinesis 承接高吞吐事件流
  3. 部署 Flink 等流式引擎或类似流处理系统做窗口聚合
  4. 将聚合结果分发至 OLAP 数据库，实现低延迟查询与读写分离
  5. 通过分区与热点拆分解决扩展性问题
  6. 通过流系统保留和副本机制保证点击不丢失
  7. 通过防伪签名机制与严格时序的防重缓存策略保证点击正确性
