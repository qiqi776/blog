云盘系统设计 ​

本文设计的是一个类似 Dropbox 或 Google Drive 的云盘系统。用户不仅要能上传和下载文件，还要能把文件分享给别人，并在多台设备之间自动同步文件变化。沿着这条主线继续展开，系统会自然涉及大文件上传、断点续传、内容去重、增量同步、全球下载加速和访问安全这些典型问题。

问题定义与边界 ​

功能需求 ​

用户能够从任意设备上传文件、从任意设备下载文件、把文件分享给其他用户、查看别人分享给自己的文件，系统能够在多个设备之间同步文件变化。

非功能需求 ​

  1. 高可用：这类文件系统通常更偏向可用性，而不是跨地域的强一致性
  2. 可靠性：文件内容不能丢失，也不能轻易损坏
  3. 低延迟：上传、下载和同步都要尽量快
  4. 可扩展性：需要支持大量文件和持续增长的用户规模
  5. 安全性：必须控制访问权限，并保护传输和存储中的数据

规模假设 ​

单文件大小最高约为 50GB，用户分布在多个地区，文件修改会持续发生，因此同步链路需要长期运行。

核心实体、接口与数据流 ​

核心实体 ​

这里最核心的实体有三类：File 文件数据、FileMetadata 文件元数据记录、User 用户信息。随着分享和同步功能展开，还会自然引出两类扩展实体：SharedFiles 共享关系映射、ChangeEvent 变更事件日志。

这里需要注意的是把文件内容和文件元数据分开：文件原始字节属于大对象数据，适合放到 Blob Storage 中；文件名、大小、MIME type、上传状态、上传者、时间戳和权限信息，则适合放到元数据数据库中。为了支持大文件与断点续传，元数据里还会逐步出现一些扩展字段，例如文件级 fingerprint、chunk 级 fingerprint、uploadId、chunks[] 状态和 ETag。

初始 API ​

  • 上传文件：POST /files
  • 下载文件：GET /files/{fileId}
  • 分享文件：POST /files/{fileId}/share
  • 查询变更：GET /files/changes?since={timestamp}

这里的 API 只是基础阶段的控制面抽象。随着系统演化，上传和下载接口通常会进一步扩展成“申请 presigned URL / signed URL”的接口，而真正的文件数据会绕开应用服务，直接在客户端与对象存储、CDN 之间流动。

高层数据流 ​

  1. 客户端向文件服务申请上传或下载凭证
  2. 文件服务完成鉴权、写入或读取元数据，并返回 presigned URL 或 CDN signed URL
  3. 客户端直接把文件内容上传到对象存储，或直接从对象存储 / CDN 下载
  4. 分享关系写入 SharedFiles
  5. 文件变化写入 ChangeEvent，供同步服务通过推送或轮询分发给其他设备

核心架构设计 ​

一、上传文件 ​

基础方案，是让客户端把文件直接传给后端文件服务，再由文件服务把文件存到本地磁盘，并把元数据写进数据库。这个方案对小系统来说能工作，但很快会暴露出明显问题：本地磁盘不容易扩展，文件越来越多之后，应用服务会同时承担业务逻辑和存储压力；这种方案不够可靠，一旦机器故障，这台机器上的文件就会不可用；后端位于大文件数据路径上，上传吞吐和应用计算资源会相互干扰。

因此，第一步改进是把文件内容放到 Blob Storage 中，例如 Amazon S3 或 Google Cloud Storage，而把元数据放到数据库中。这样，文件本体的存储、耐久性和扩容交给对象存储，应用服务只负责元数据和业务逻辑。但这个方案还有一个问题：客户端先把文件传给后端，后端再把文件写到对象存储，相当于文件被传输了两次，这样既慢又贵。

更好的方式是让客户端直接上传到 Blob Storage，具体流程变成：客户端先向后端请求一个 presigned upload URL；后端创建元数据记录，把状态写成 uploading；后端把 presigned URL 返回给客户端；客户端直接用这个 URL 把文件上传到对象存储；对象存储通过事件通知后端上传已完成；后端把文件状态更新为 uploaded。到了这里，文件服务已经不再负责搬运文件本体，而是退到控制面位置，只负责生成 URL、写元数据和处理状态变化。

二、下载文件 ​

下载链路的演进方式和上传几乎一致。常见但不够理想的做法，是后端先从对象存储把文件取出来，再转发给客户端，这样仍然是双重传输：一次从对象存储到后端，一次从后端到客户端。更合理的改法是让客户端直接从对象存储下载，后端只在前面做权限校验，并给客户端签发一个 presigned download URL。这样，数据路径就从“客户端 -> 后端 -> 对象存储”收敛成了“客户端 -> 对象存储”。

不过，这里还需要继续往前推一步。即使已经是对象存储直连，对全球用户来说仍然可能很慢，因为对象存储通常只在单个区域里，距离远的用户依然要跨地域访问。因此，更完整的方案是在对象存储前加一层 CDN，后端不再给客户端直接返回 S3 地址，而是返回 CDN 的签名 URL。这样，文件第一次请求时由 CDN 回源，后续请求会从边缘节点直接返回，从而显著降低下载延迟。这里也有一个工程代价：CDN 是贵的，不能无脑缓存所有文件。实际系统里需要结合 cache-control、TTL 和失效策略，决定哪些文件值得缓存、缓存多久，以及文件更新后如何做主动失效。此外，大文件下载通常还会配合 HTTP Range Request，这样客户端可以做断点续传、拖动定位，甚至并行下载不同字节区间。

三、分享文件 ​

分享关系最初可以直接放在 FileMetadata 的 shareList 里，记录这个文件分享给了哪些用户。这样做在校验权限时很直接，只要看看当前用户是否在 shareList 中就行。但这个结构有一个明显问题：用户打开自己的首页时，系统不仅要展示他自己上传的文件，还要展示别人分享给他的文件。前者可以通过 uploadedBy 很容易查到，但后者如果还依赖 shareList，就会变成一次代价很高的逆向查询，系统必须扫描大量文件，看这个用户是否出现在别人的分享列表里。

一个中间方案是除了原来的 shareList 之外，再额外维护一份从用户到文件列表的缓存，也就是一份“谁收到了哪些分享”的反向映射。这样读取会快很多，但缺点是需要维护两份数据的一致性。最后，更稳妥的方案是直接把共享关系单独建模，新增一张 SharedFiles 表，记录 userId -> fileId 的映射。在这种设计里，查询某个用户收到了哪些文件会变成一次按用户查映射，原来的 shareList 甚至可以不再保留，权限模型会更干净。这里还有一个小的工程细节：如果用 DynamoDB，可以把 userId 作为 partition key，把 fileId 作为 sort key；如果用关系型数据库，则可以把它们做成联合主键。重点不是数据库名字本身，而是共享关系应该围绕查询模式来设计。

四、同步文件变化 ​

同步天然分成两个方向：Local -> Remote 和 Remote -> Local。对于 Local -> Remote，客户端需要有一个本地同步代理，它监听本地文件夹变化，例如 Windows 的 FileSystemWatcher 或 macOS 的 FSEvents。当文件被创建、修改或删除时，同步代理会把对应任务写入本地状态或本地队列，再调用上传接口把变化发到远端。这里采用的是很务实的冲突策略：last write wins，也就是说如果两个设备同时改了同一个文件，就以最后一次写入为准。它不是最理想的冲突解决方式，但足够简单，适合作为基础版本；版本控制和冲突副本可以作为后续扩展单独讨论。

对于 Remote -> Local，系统要解决的是客户端怎么知道远端有变化。最简单的方案是轮询，客户端周期性调用 GET /files/changes?since={timestamp}，优点是实现简单，缺点是实时性差，而且没有变化时也会浪费带宽。另一种方案是 WebSocket 或 SSE，也就是由服务端主动推送变化通知给客户端，这样可以做到接近实时，但连接管理和可靠性会更复杂。最终推荐的是混合模式：正常情况下客户端维持一条 WebSocket 或 SSE 长连接，服务端通过它主动推送变化；同时客户端保留周期性轮询作为兜底。这样做的原因很直接：长连接实时性好，但可能断；轮询慢一点，但能作为恢复路径。两者结合之后，系统既能有较好的同步体验，又能保证最终不会漏掉变化。

架构收束 ​

当上传、下载、分享和同步四条链路都讲完之后，系统通常由下面几部分组成：Uploader / Downloader / Client App、LB & API Gateway、File Service、File Metadata DB、SharedFiles、Blob Storage、CDN、Sync Service。其中，File Service 的职责非常清楚：它负责读写元数据、校验权限、生成 presigned URL 或 CDN signed URL，并协调客户端和对象存储之间的关系，本身不直接承载文件上传和下载流量。生成 presigned URL 是本地签名操作，不需要真的去请求 S3，这一点也解释了为什么文件服务不会成为对象存储的转发代理。

深入讨论 ​

一、如何支持大文件 ​

大文件上传是云盘系统里最关键的深入问题。它最直观的两个症状，是用户需要看到进度条，并且需要支持 pause 和 resume。如果一个 50GB 的文件直接走单个 POST 请求，会遇到一系列问题：用户根本不知道上传是否还活着，也无法优雅地暂停和恢复；网络中断之后只能从头再来；浏览器、网关和服务端都可能有请求大小限制和超时限制。如果上传带宽只有 100Mbps，传一个 50GB 文件大概需要一小时左右，显然不适合靠一个普通 HTTP 请求完成。除此之外，现代网关本身也常常对请求体有硬限制，例如 API Gateway 这类托管入口服务就不允许任意大的请求体通过。因此结论很明确：大文件不能作为单个请求整体上传，而必须在客户端先切成多个 chunk，再逐块传输。这里还需要避免一个常见误区：不要在服务端分块。因为如果文件已经完整传到服务端，分块这件事就失去了大部分意义，超时、恢复和进度这些核心问题仍然没有解决。真正有效的分块一定发生在客户端。

一个自然的做法，是让客户端把文件拆成 5MB 到 10MB 左右的块。这样一来，每块上传都更容易成功，客户端可以按块更新进度条，网络中断后只需要重传失败的部分。但分块之后立刻会出现一个新问题：系统怎么知道哪些块已经上传了，哪些还没上传？一个可用但不够可靠的方案，是在 FileMetadata 中加入 chunks 字段，记录每个 chunk 的状态，例如某个文件当前可能处于 uploading 状态，同时内部有一组 chunk，其中一部分已经 uploaded，一部分仍然是 not-uploaded。这样客户端在恢复上传时，只要查一下这份元数据，就能知道从哪继续。这个设计的优点是简单，客户端也能立即看到最新进度；但问题在于，它过于依赖客户端自报，恶意客户端完全可以在根本没有上传 chunk 的情况下伪造一个 PATCH 请求，把所有 chunk 都标成 uploaded。虽然它最多污染的是自己的文件状态，而不是别人的数据，但系统会进入难以排查的不一致状态。

因此，更稳妥的做法是 trust but verify，也就是说客户端可以继续上报每个 chunk 的进度，用来改善用户体验，但后端不能只听客户端的，而必须通过对象存储的服务端 API 做校验。标准做法就是把整个过程升级成真正的 multipart upload：客户端发起上传请求；后端调用对象存储的 CreateMultipartUpload，拿到一个 uploadId；后端为每个 partNumber 生成对应的 presigned URL；客户端逐块上传，每块上传成功后拿到对应的 ETag；客户端把 chunk 状态和 ETag 回传给后端；后端调用 ListParts 校验这些 part 是否真的存在；全部 part 都确认无误后，后端调用 CompleteMultipartUpload；最后再把文件状态更新为 uploaded。这样一来，系统就把“进度更新”和“最终确认”分开了，进度可以相信客户端一点，以便及时反馈给用户；但最终文件是否真的上传成功，必须由后端通过对象存储来确认。ListParts + ETag 的校验就是这个方案真正可靠的关键

接着追问：如何判断“这是不是之前传过的同一份文件”？这里就引出了 fingerprint，它是文件内容的哈希，不是文件记录 ID。两个不同用户上传同样内容的文件，会有不同的 fileId，但会得到相同的内容 fingerprint。这个字段能够解决两个关键问题：这份内容此前是否已经出现过，以及这次中断的上传是不是某次历史上传的续传。进一步细化之后，chunk 本身也可以有自己的 fingerprint，这样客户端恢复上传时，不仅能知道“是不是同一份文件”，还可以精确知道“哪些块已经存在，哪些块需要继续传”。于是，断点续传和内容去重就自然联系起来

完整的大文件上传流程可以收束为：客户端先为整份文件计算 fingerprint；客户端再为每个 chunk 计算 fingerprint；客户端先问后端是否已有相同 fingerprint 的文件或未完成上传；如果存在未完成上传，就恢复已有 uploadId 和 chunk 状态；如果不存在，就创建新的 multipart upload；客户端拿到每个 chunk 的 presigned URL 后逐块上传；客户端持续把 chunk 状态和 ETag 回传后端；后端通过 ListParts 校验后，调用 CompleteMultipartUpload；文件状态最终转为 uploaded。上传完成之后，在对象存储视角里它又会重新表现为一个普通对象，因此下载链路并不需要理解 chunk 的内部细节，只要继续走 CDN + Range Request 即可。

二、如何支持更快的上传、下载和同步 ​

速度的第一层优化在高层设计里已经体现过了：让数据尽量绕开应用服务，直接在客户端和对象存储、CDN 之间流动。但这还不够，因为“更快”并不只等于“走直连”，这里可以把性能优化继续拆成三个方向

第一个方向是利用 chunk 本身提升吞吐。分块不仅仅是为了断点续传，它同样能提高速度，因为多个 chunk 可以并行上传，从而更充分地利用带宽。客户端甚至还可以根据网络环境动态调整 chunk 大小：网络不稳定时块可以更小，以降低失败代价；网络稳定时块可以稍大，以减少调度开销。

第二个方向是压缩。压缩能减少传输字节数，因此在很多情况下会缩短上传和下载时间，但它不是总值得做，因为压缩和解压都会消耗 CPU，收益取决于文件类型。文本类文件往往能压得很好，而图片、视频、音频这类已经压缩过的格式，进一步压缩往往收益很低。一个更合理的工程原则是：如果要压缩，最好在客户端完成，可以按需选择 gzip、brotli 或 zstd；后端继续保持在控制面，而不是重新进入数据传输路径；如果同时还要加密，通常应该先压缩再加密，因为加密之后数据会接近随机，压缩几乎失效

第三个方向是增量同步，也就是 delta sync。理想情况下，一个文件如果只改了一小部分，就不应该重传整份文件，而是只传变化过的部分。这里需要特别注意固定大小分块的一个问题：如果总是按固定字节数切块，那么只要文件前面插入一个字节，后面的所有块边界都会整体漂移，导致后面几乎所有 chunk 的 hash 都变了，增量同步就会失效。因此，更好的做法是使用 Content-Defined Chunking，也就是说分块边界由内容本身决定，而不是由固定大小决定。这样即便文件前部发生小改动，也只会影响局部 chunk，不会把后面所有块整体“推歪”。这一步是性能部分最有技术含量的点之一，因为它直接决定了 delta sync 是否真正可行

性能优化的优先级大致是：先让上传和下载绕开应用服务，直接连接对象存储和 CDN；再用 chunk 并行上传提高带宽利用率；再根据文件类型决定是否压缩；最后在同步路径上引入内容定义分块，真正实现增量同步。

三、如何确保文件安全 ​

文件安全可以从三个关键层面展开。第一层是传输安全：上传和下载都必须走 HTTPS，防止文件内容在网络中被窃听，这一层对应的是“文件在路上”的安全。第二层是静态存储安全：文件在对象存储里应当启用 encryption at rest，这样即便底层磁盘或存储介质泄露，也不会直接暴露出文件明文，这一层对应的是“文件躺在存储里”时的安全。第三层是访问控制：无论系统最终保留的是 shareList，还是拆出来一张 SharedFiles 表，本质上它们都承担 ACL 的角色，也就是定义“谁有资格访问哪个文件”。后端在给用户签发下载链接之前，必须先检查这些权限关系，确保用户确实拥有访问权。

在访问控制之上，签名 URL 的短时有效性也非常关键。无论是 S3 presigned URL 还是 CDN signed URL，都不应该长期有效，它们的作用不是替代权限系统，而是在权限系统已经通过之后，再给客户端一个短时间可用的下载入口。这样设计有两个直接好处：即使链接被复制或转发，风险窗口也有限；对象存储和 CDN 仍然不需要直接理解业务权限模型，它们只需校验签名即可。安全这一段的核心理念是：权限边界必须掌握在我们的控制面里，而文件数据面只通过短期签名 URL 暂时开放。在更严格的场景下，还可以进一步叠加 IP 绑定、一次性 URL、签名 Cookie 或服务端下载审计日志等限制
