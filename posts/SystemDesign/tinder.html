Tinder 交友系统设计 ​

Tinder 这类交友系统的核心体验，是让用户持续看到一组符合条件、距离足够近的候选人卡片，并通过左滑或右滑表达跳过或喜欢。当两个人都对彼此右滑时，系统需要立即形成 match，并通知双方。

从表面看，它像是一个 feed 页面加一个 swipe 写接口。但系统复杂度主要集中在三件事上：如何低延迟生成潜在匹配候选池，如何在高并发下保证 swipe 与 match 判断的一致性，以及如何避免把已经滑过的人反复展示给用户。

问题定义与边界 ​

功能需求 ​

  • 用户能够创建个人资料和偏好设置
  • 用户能够看到符合条件且距离足够近的候选人卡片
  • 用户能够对候选人左滑 / 右滑
  • 双方都右滑时，系统能够通知 match

非功能需求 ​

  1. Swipe 一致性要强：互相右滑时不能漏掉 match
  2. 系统需要支撑大规模日活，例如 20M DAU
  3. 候选池加载延迟要低，目标约 < 300ms
  4. 系统应避免重复展示已滑过的候选人

本文暂不展开 ​

  • 图片上传
  • 匹配后的私信聊天
  • 超级喜欢、付费加速等高级功能
  • 反作弊与假资料治理

核心实体、接口与数据模型 ​

核心实体 ​

  • User
  • Swipe
  • Match

这里的 User 既是系统账号，也是会被别人展示和滑动的 profile。

Swipe 至少要表达 fromUserId、toUserId、direction（例如 left 或 right）以及 createdAt。Match 则表示两个用户已经互相右滑。

初始接口 ​

  • 更新资料：POST /profile
  • 获取候选池：GET /feed?lat={lat}&lon={lon}
  • 提交滑动：POST /swipes

典型的 swipe 请求可以长成：

json
{
  "toUserId": "u2",
  "direction": "right"
}

基础数据模型 ​

User 包含 userId、gender、interestedIn、age、interests、maxDistance、location。

Swipe 的主键为 fromUserId + toUserId，值为 direction、createdAt。

Match 的主键为规范化后的 (userA, userB)。

核心架构设计 ​

一、用户能够创建资料和偏好 ​

资料更新链路可以先保持简单：Client 请求进入 API Gateway，再由 Profile Service 写入 Profile DB。当用户提交 POST /profile 时，服务保存年龄偏好、兴趣、最大距离、位置等信息。这一层的技术难度不高，但它会直接决定后续候选池生成时可以使用哪些过滤条件。

二、用户能够看到潜在匹配候选池 ​

基础方案，是每次用户打开 App 时直接查询数据库，把符合偏好条件的人查出来。伪 SQL 大概会像这样：

sql
SELECT *
FROM users
WHERE age BETWEEN 18 AND 35
  AND interestedIn = 'female'
  AND lat BETWEEN userLat - maxDistance AND userLat + maxDistance
  AND lon BETWEEN userLon - maxDistance AND userLon + maxDistance;

这个方案在功能上成立，但规模一上来就会吃力：地理位置查询本身很重，候选池还要叠加偏好筛选，并且必须排除已经滑过的人。因此，高层设计可以先把它作为基础版本；真正影响体验的低延迟候选生成，则放到后续深入讨论中解决。

三、用户能够左右滑并形成 match ​

基础版本可以单独引入 Swipe Service 和 Swipe Store。最直观的流程是：用户提交 swipe，系统先检查“对方之前是否已经对我右滑”；如果对方已经右滑，而且本次也是右滑，则创建 Match；无论是否形成 match，都把本次 swipe 记录持久化。

到这里，左滑 / 右滑能落库，双向右滑时能形成匹配。但这个基础版会遇到竞态条件，后面还需要继续优化。

深入讨论 ​

一、如何让 feed 低延迟又符合地理位置筛选 ​

直接在主数据库里做位置筛选通常会很慢，尤其是在用户量很大、位置持续变化的场景下。更合适的方向，是把“候选人检索”从通用数据库查询升级为 geospatial index，再在候选集合上叠加偏好过滤。

这里有两种典型路径。第一种是使用地理索引数据库或搜索引擎，例如 Elasticsearch / OpenSearch，或者支持 geo query 的数据库。系统可以先按位置快速筛出候选集合，再叠加年龄、兴趣、性别偏好等条件。第二种是把预计算与索引查询结合起来：对大多数用户，后台先准备一批候选池并写入缓存；当用户快滑完时，再从地理索引系统里补充新的候选。这样，候选池既不是完全实时生成，也不是完全静态预计算，而是 cached feed + indexed realtime refill 的混合模式。

二、为什么要预计算候选池 ​

如果每次用户进入 App 都实时查询位置、偏好和已滑过集合，查询链路会很长，延迟也很难稳定压到 < 300ms。更好的思路，是在后台提前给用户准备一批 profile stack。用户打开 App 时，服务直接从缓存中读取候选 ID，再批量补全 profile 详情。这样首屏候选卡片的加载延迟会明显降低。

常见做法是把候选池缓存到 Redis。每个用户保留一小批待滑 profile ID，当剩余候选不足时异步补货。这样在用户视角里，feed 会接近“无限可滑”；从系统角度看，本质是在用预计算和缓存换取稳定的低延迟。

三、预计算候选池为什么会 stale ​

预计算一旦引入，就会带来候选池过期的问题。常见情况包括：对方已经移动到很远的位置，对方修改了偏好后不再符合条件，或者对方已经被当前用户滑过但缓存还没来得及清掉。

因此，cached feed 不能被当成绝对真相，更像一个候选草稿池。在展示某个 profile 前，系统仍然应该做一层轻量校验，例如检查对方是否仍在距离范围内、是否已被当前用户滑过、是否仍满足基础偏好。预计算负责省掉大部分昂贵查询，展示前 validation 则负责兜住体验和正确性。

四、如何避免把滑过的人再次展示 ​

重复展示已滑过的人会严重破坏体验。一个直接方案是在 Swipe Store 里保存每个用户的滑动历史，生成候选池时把这些 toUserId 排除掉。但如果每次都实时查询一个巨大的“已滑集合”，成本会很高。

更常见的做法是分层处理：持久化层保存完整 swipe 历史，缓存层维护用户最近的已滑 ID 集合，feed 生成时优先用缓存快速排除。这样既能避免重复展示，又不需要每次都把历史 swipe 全量拿出来过滤。

五、如何保证 swipe 和 match 的一致性 ​

最有代表性的竞态发生在双方几乎同时右滑时：A 对 B 右滑，B 也几乎同时对 A 右滑。两边都先查“对方是否已经右滑我”，查询时都还看不到对方的新记录，于是最后两边都写入了 swipe，但没有任何一边创建 match。结果是两个人明明已经互相喜欢，却永远看不到匹配结果。

因此，swipe 记录和“是否互相右滑”的判断，最好在一次原子操作里完成。一种实现方式是借助 Redis 的原子能力：用同一个 key 存两边的 swipe 状态，通过 Lua script 在一次执行里先写入自己的 swipe，再读取对方的 swipe，最后决定是否形成 match。这里的关键不是 Lua 本身，而是明确这条链路需要强一致 / 原子更新，不能依赖“先查再写”的分离流程。

六、为什么单独拆出 Swipe Service ​

Profile 更新和 swipe 写入的访问模式差异很大：用户修改资料的频率较低，而滑动行为的频率高得多。因此，把 Swipe Service 和 Profile Service 拆开更容易扩展。swipe 路径可以单独扩容，swipe 存储也可以按高写入场景优化，feed 读路径和 swipe 写路径不会互相拖累。这是一种按访问模式拆分服务的典型思路。

七、如果候选池滑完了怎么办 ​

即使有缓存池，活跃用户也可能很快滑完。因此系统通常会在候选池剩余不多时提前触发补货。例如，当剩余 profile 少于 N 个时，后台异步从索引系统拉取一批新的候选，再写回缓存。

这能让用户几乎感觉不到“加载下一批候选”的停顿。从体验角度看，feed 像是无限的；从系统角度看，这是典型的提前预取。

八、虚假资料和过期位置如何处理 ​

这两个问题都很常见，但它们属于主链路之外的扩展治理。过期位置可以通过位置 TTL、进入 App 时重新上报位置、展示前复核等方式缓解。虚假资料则更接近风控 / trust & safety 子系统，需要独立建模和评估，不适合混入候选池与 match 的主流程。

整体链路 ​

更新资料路径 ​

  1. 用户请求 POST /profile
  2. Profile Service 写入资料和偏好
  3. 后台异步更新其可被检索索引

获取候选池路径 ​

  1. 用户进入 App
  2. 系统优先从缓存里读取预计算候选池
  3. 展示前做轻量过滤，排除已滑过和明显 stale 的 profile
  4. 候选不足时，异步从地理索引 / 搜索系统补货

滑动路径 ​

  1. 用户左滑 / 右滑一个 profile
  2. 请求进入 Swipe Service
  3. Redis / 原子脚本写入本次 swipe
  4. 同时检查对方是否已右滑
  5. 若双方互相右滑，则创建 Match
  6. 已滑对象写入排除集合，避免再次展示

总结 ​

Tinder 交友系统的主线可以分为几步：

  1. 先用 Profile、Swipe、Match 三个核心实体把问题边界立住
  2. 用地理位置 + 偏好筛选解释候选池的基本生成逻辑
  3. 用缓存候选池解决 feed 首屏低延迟
  4. 用索引系统做补货，解决“无限滑”的体验
  5. 用已滑集合避免重复展示
  6. 用原子 swipe + match 检查解决一致性问题

整体来看，这套系统本质上是基于地理位置和偏好条件的候选推荐系统，外加一条需要强一致匹配判断的高频写链路。
