YouTube 视频平台系统设计 ​

本文讨论的是一个类似 YouTube 的视频分享平台。用户需要能上传视频，其他用户能够低延迟地观看视频，而且在网络条件较差时仍然应该尽量平滑播放

它表面上只有两个核心功能：上传视频和观看视频。但这两个功能一旦放到大规模和真实网络环境里，问题会立刻复杂起来。我们需要考虑清楚这三件事：大文件如何高效上传；上传后的视频如何处理成可播放格式；播放时如何根据网络状况自适应切换清晰度

问题定义与边界 ​

功能需求 ​

用户能够上传视频，用户能够观看视频

非功能需求 ​

  1. 高可用：优先可用性，允许最终一致
  2. 支持大文件：单个视频可能达到数十 GB
  3. 低延迟播放：用户点开视频后应尽快开始观看
  4. 弱网可用：网络变差时应尽量继续播放，而不是一直卡顿
  5. 可扩展：大约支持 1M 视频 / 天上传、100M 视频 / 天观看
  6. 支持断点续传 / resumable uploads
  • 本文暂不展开评论、点赞、订阅，搜索和推荐，版权审核和内容安全，观看统计和广告系统

核心实体、接口与数据模型 ​

核心实体 ​

  • User
  • Video
  • VideoMetadata

VideoMetadata 包含标题、描述、上传者、处理状态、manifest URL 等结构化信息；视频二进制内容是真正的音视频数据，放在 blob storage

初始接口 ​

  • 申请上传：POST /videos/presigned-upload
  • 获取视频元信息：GET /videos/{videoId}

基础数据模型 ​

VideoMetadata 至少需要记录 videoId、uploaderId、title、description、status、originalObjectKey、manifestUrl 和 createdAt。其中 status 一般会经历 uploading、processing、ready 和 failed 这几个阶段

核心架构设计 ​

一、用户能够上传视频 ​

最差的做法，是客户端直接把整个大视频传给应用服务器，再由应用服务器落盘或转存对象存储。这个方案的问题很明显：应用服务器会被大文件 I/O 占满；网络路径多了一跳；大文件上传失败后恢复成本很高；应用层会承担完全没必要的数据搬运工作

更合理的方案是走大对象直传模式：客户端先请求 POST /videos/presigned-upload；服务端创建一条 VideoMetadata 记录，状态设为 uploading，返回 presigned URL 或分片上传信息；客户端直接把视频上传到对象存储；对象存储在上传完成后触发事件；系统把视频状态推进到 processing。这一步和 Dropbox / Google Drive 的上传链路非常相似，核心思想都是应用服务退回控制面，文件本体绕开应用服务直达对象存储

二、使视频可播放 ​

这里最容易误解的是以为上传完就等于用户可以看。实际上，用户上传的视频原格式很可能并不适合直接播放，不同设备支持的编码和封装格式各异，原文件可能过大不适合直接流式传输，如果只存完整文件客户端无法高效按段播放。因此，上传后的下一步是视频处理流水线

对象存储发出上传完成事件；Video Processing Service 消费事件并读取原始视频；执行转码、切片和 manifest 生成；把处理结果重新写回对象存储；更新 VideoMetadata.manifestUrl；把状态改为 ready

三、用户能够观看视频 ​

播放接口直接让客户端下载整个视频文件，不算真正意义上的流式播放。用户要先下载很大一段甚至整个文件才能开始播放；网络抖动时容易从头重来；弱网下长时间卡住；根本无法根据网络动态切换清晰度。所以更合理的方向是基于切片和 manifest 的流式播放

客户端观看时的基本步骤通常是：请求 GET /videos/{videoId}；服务端返回 VideoMetadata，其中包含 manifest 文件的 URL；客户端先拉 manifest，再按 manifest 指引逐段下载视频 segment；下载一小段后立即开始播放，并在后台继续拉后续 segment。这就把“整个文件下载”改成了“按段增量拉取”，用户会更快看到首帧

深入讨论 ​

一、为什么不能只存原始视频 ​

上传到对象存储里的原文件不是最终播放对象。如果系统只保存原始文件，会遇到两个核心问题：设备兼容性差，不同终端支持的格式不同；播放体验差，无法很好地做切片流式传输。所以更好的设计至少要做到把同一视频转成多种可播放格式，但这还不够，因为如果每种格式还是一个完整大文件，播放时仍然不够灵活

二、为什么最终要存成多格式 + 多切片 ​

将视频切割为大量小片段，并对每个片段生成不同码率/格式的版本，最后通过 manifest 文件将它们组织起来。这套架构能同时满足多设备兼容、快速首帧启动、增量下载以及网络波动时动态切换质量等需求。视频处理流水线因此天然会形成一张 DAG：原始文件先切片，各片段再并行转码为不同清晰度版本，最终汇总生成 manifest。整条链路中最重的计算环节通常是转码，非常适合用大量 worker 并行执行

三、观看为什么不能只做“分段下载” ​

相较于整文件下载，分段下载已有明显进步，能让用户更快开始播放。但如果系统始终固定下载某一种清晰度的片段，问题仍未根治：用户网络恶化时，高码率片段可能来不及下载完毕而导致卡顿；网络好转时，系统也无法自动升级清晰度。因此，更优解是采用自适应码率流（ABR），它依赖两个前提：视频已被切片；每个切片已具备多种码率/格式的版本。配合 manifest 文件，客户端即可根据实时网络状况自行决策

四、自适应码率播放是怎么工作的 ​

客户端的典型播放路径为：获取 VideoMetadata → 拉取主 manifest → 选择一个初始码率版本 → 下载首个片段并开始播放 → 后台继续拉取后续片段。若监测到带宽下降，自动切换到更低码率的片段；若网络恢复，再切回更高清晰度。这一设计的重点在于：播放体验的优化并不全由服务端完成，客户端播放器本身承担了关键的决策逻辑，成为更主动的参与者

五、如何处理上传后的长时间处理任务 ​

视频上传完毕后的处理并非瞬时操作，超长视频的转码与切片可能持续较久。因此，系统天然适合采用多阶段异步任务：上传完成事件进入队列；处理任务由 worker 异步消费；各片段的转码可并行执行；全部步骤完成后，视频状态才更新为 ready。这意味着用户上传的视频通常不会立即对外可见，而是经历一个 processing 状态。在面试中明确指出这一点尤为重要，它体现你理解这不是一个同步请求内可以完成的流程

六、为什么 blob storage 前面通常还要有 CDN ​

进入观看阶段后，系统压力从“写大文件”切换为“海量读”。热门视频会被大量重复访问，如果所有片段都直接从对象存储源站读取，延时更高、跨地域体验差且带宽成本昂贵。更自然的方案是将视频片段和 manifest 存放于对象存储，并在前面接入 CDN，客户端大部分时候从边缘节点拉取片段。这样可同时改善读延迟、跨地域体验并降低源站压力，本质上属于扩展读取的关键一步

七、如何支持 resumable uploads ​

要求支持断点续传，因此上传链路不能仅依赖单一的大型 PUT 请求。更合理的做法是采用分片上传：客户端将原始视频按块上传，每块成功后记录进度；网络中断后，只需重传失败的分块即可。这与大文件直传模式中的断点续传设计完全同构，面试时可明确指出该模式会复用直传加分片上传这一套组合

八、为什么 metadata DB 和 blob storage 要分开 ​

视频元数据与二进制内容的访问模式完全不同：元数据是小对象，按 videoId 点查，需频繁更新状态；视频内容则是超大 blob，一次写入多次读取，极适合对象存储。若将两者强行塞入同一系统，元数据查询会变得沉重，大文件处理也会污染常规读写。因此，分层是自然选择：VideoMetadata DB 保存结构化信息，Blob Storage 负责视频本体及切片

整体链路 ​

上传路径 ​

  1. 客户端请求 POST /videos/presigned-upload
  2. 服务端写入 VideoMetadata(status=uploading)
  3. 返回 presigned URL / multipart upload 信息
  4. 客户端直传对象存储
  5. 上传完成后触发事件
  6. 状态进入 processing

处理路径 ​

  1. Video Processing Service 消费上传完成事件
  2. 拉取原始视频
  3. 切片
  4. 并行转码成多个 bitrate / format
  5. 生成 manifest 文件
  6. 把所有产物写回对象存储
  7. 更新 VideoMetadata.manifestUrl
  8. 状态改为 ready

播放路径 ​

  1. 客户端请求 GET /videos/{videoId}
  2. 服务端返回 VideoMetadata
  3. 客户端下载 manifest
  4. 从 CDN 逐段拉取视频 segment
  5. 根据网络状况动态切换 bitrate
  6. 持续播放后续 segment
