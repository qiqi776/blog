抽象：进程 ​

进程是正在运行的程序

程序是磁盘上静态的指令和数据集合，无生命周期；进程是程序运行时的动态实例，有生命周期

时分共享：操作系统通过让一个进程运行一小段时间，然后暂停它并运行另一个进程，如此循环。资源由不同实体在不同时间段轮流使用 空分共享：资源在空间上划分给不同实体独占，如磁盘空间 代价：性能开销。CPU 必须在进程间共享，单进程的感知执行速度会下降

操作系统通过CPU 虚拟化，利用时分共享技术给每个进程提供一种拥有独立 CPU 的假象

进程是操作系统为运行的程序提供的抽象，要描述一个进程，必须明确其在运行期间可访问或修改的所有系统组件

  • 内存：存放指令（代码）、静态数据、堆和栈
  • 通用寄存器、程序计数器 (PC/IP)、栈指针和帧指针、I/O 状态

现代操作系统提供了必要的API

  • 创建：在 shell 中键入命令或双击应用程序图标时，会调用操作系统来创建新进程，运行指定的程序
  • 销毁：系统提供了一个强制销毁进程的接口
  • 等待：有时等待进程停止运行是有用的，因此经常提供某种等待接口。
  • 其他控制：例如，大多数操作系统提供某种方法来暂停进程，然后恢复
  • 状态：操作系统提供接口来获得有关进程的状态信息

进程创建流程 ​

  1. 加载：将代码和静态数据从磁盘读取到内存（进程地址空间）。早期系统在运行前一次性全部加载，而现代系统使用了懒加载，仅在程序执行需要时才加载对应的代码/数据片段（通过分页/交换机制实现）
  2. 栈分配：为运行时栈分配内存。初始化栈：填入 main() 函数的参数 argc, argv
  3. 堆分配：为动态内存分配 malloc/free 预留空间
  4. I/O 初始化：建立输入/输出和错误的文件描述符
  5. 启动：跳转到 main() 入口，将 CPU 控制权移交给新进程

进程状态 ​

进程在生命周期中主要处于三种状态，状态转换由操作系统调度决定

  • 运行：进程正在 CPU 上执行指令
  • 就绪：进程已准备好运行，但操作系统尚未安排其执行
  • 阻塞：进程正在等待某些事件发生（如磁盘 I/O 完成），此时不占用 CPU

数据结构 ​

操作系统内核需要维护数据结构来追踪所有进程的信息

  • 进程列表：记录系统中所有进程

  • PCB：存储单个进程的详细信息，xv6 中对应的结构体是 struct proc:

  • char *mem：进程内存起始地址

  • enum proc_state state：当前状态

  • int pid：进程标识符

  • struct context context：上下文保存区。用于进程切换时保存寄存器（eip, esp, ebx 等），以便后续恢复运行

  • struct file *ofile[]：打开的文件列表

  • 特殊状态：进程已退出，但父进程尚未调用 wait() 读取其返回代码。此时进程已停止运行，但其 PCB 仍保留在系统中以便父进程检查

插叙：进程API ​

fork()系统调用 ​

fork() 是操作系统用于创建新进程的核心接口

当进程调用 fork() 时，操作系统会创建一个子进程。子进程是父进程的几乎完全拷贝。它获得父进程的地址空间、寄存器状态、程序计数器 PC 以及打开的文件描述符的副本

子进程不会从 main() 函数开始执行。它会直接从 fork() 系统调用的返回处开始执行，就好像子进程自己刚刚调用了 fork() 一样

一次调用，两次返回。这是 fork() 最显著的特征，也是二者的不同点，用于区分父子进程：

  1. 父进程 fork() 返回新创建的子进程的 PID
  2. 在子进程中 fork() 返回 0
  3. 出错时返回负数

利用返回值的不同，编写分支逻辑来决定父子进程各自的行为：

c
int rc = fork();
if (rc < 0) {
    // fork 失败
    exit(1);
} else if (rc == 0) {
    // 子进程代码块 (由于返回值为0，只有子进程会进入此分支)
} else {
    // 父进程代码块 (rc 为子进程 PID，只有父进程会进入此分支)
}

fork() 创建进程后，系统中存在两个活跃进程。操作系统不保证父子进程的执行顺序，哪个进程先运行，完全取决于 CPU 调度程序的策略

  1. sys_fork：在 xv6 中，fork 会调用 allocproc 在进程表中分配一个空闲槽位，并生成新的 PID
  2. 内存复制：在 xv6 中，这是通过 uvmcopy 函数实现的，它将父进程页表和物理内存内容逐页复制给子进程
  3. Trap Frame：子进程之所以能从 fork 返回并获得 0，是因为内核在创建子进程时，显式地将子进程 Trap Frame 中的 a0 寄存器设置为 0

wait()系统调用 ​

父进程调用 wait() 后，其执行会被暂停，父进程进入阻塞状态，不占用CPU。直到子进程执行完毕（调用 exit() 或结束），wait() 才会返回子进程的 PID

c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

int main(int argc, char *argv[])
{
    printf("hello world (pid:%d)\n", (int)getpid());

    int rc = fork();
    if (rc < 0) {                 // fork failed
        fprintf(stderr, "fork failed\n");
        exit(1);
    } else if (rc == 0) {          // child process
        printf("hello, I am child (pid:%d)\n", (int)getpid());
    } else {                       // parent process
        int wc = wait(NULL);
        printf("hello, I am parent of %d (wc:%d) (pid:%d)\n",
               rc, wc, (int)getpid());
    }

    return 0;
}

通过引入 wait()，执行结果变得确定。无论 CPU 调度器如何选择，输出顺序一样：子->父

在 xv6 的实验中，wait 的机制是理解进程生命周期的关键：

  1. 回收资源：wait() 不仅是同步，更是为了回收子进程的资源。如果子进程退出而父进程不调用 wait()，子进程会变成僵尸进程，其占用的内核栈和 PCB 不会被释放
  2. xv6 实现：在 xv6 内核代码中，wait 系统调用会扫描进程表，寻找状态为 ZOMBIE 的子进程。如果找到，它会释放子进程的内核栈和页表，并返回子进程 PID；如果子进程还在运行，父进程会通过 sleep 进入休眠

exec()系统调用 ​

exec() 的目的是在当前进程的上下文中运行一个全新的程序

加载并运行一个新的可执行程序，替换当前进程的执行映像，PID不会改变，仍然是同一个进程，只是内容发生了变化

当进程调用 exec()（如 execvp）时：

  1. 加载：从磁盘读取指定的可执行文件（例如 wc）
  2. 覆写：使用新程序的代码和静态数据分别覆写当前进程的代码段和静态数据区
  3. 重置：重新初始化堆和栈，将参数传递给新进程的入口函数
  4. 执行：操作系统开始执行新程序，通常从 main 或 _start 开始

关键特性：永不返回

  • 成功时：exec() 调用永远不会返回，调用 exec() 的原程序的代码段已被覆盖，后续的指令（如 printf("this shouldn't print out")）在内存中已不存在，程序流直接转入新程序的入口
  • 失败时：如果 exec() 执行失败（例如找不到文件），它会返回 -1，并设置 errno。因此，exec() 调用后的代码通常用于处理错误
c
// 子进程部分
} else if (rc == 0) {
    char *myargs[3];
    myargs[0] = strdup("wc");   // 程序名
    myargs[1] = strdup("p3.c"); // 参数
    myargs[2] = NULL;           // 哨兵值，标记数组结束
    execvp(myargs[0], myargs);  // 执行 wc
    printf("this shouldn't print out"); // 只有 execvp 失败才会执行到这里
}
  • 执行流：p3 程序启动 fork() 创建子进程 子进程调用 execvp() 子进程变身为 wc 程序，运行结束并退出
  • 父进程视角：父进程 wait() 等待的是 PID 为 29384 的进程。尽管该进程的内容从 p3 变成了 wc，但 PID 未变，所以父进程能正确接收到子进程的退出状态

在 xv6 中

  1. ELF 格式：在 xv6 中，sys_exec 会解析 ELF文件头，按照段表将代码段和数据段加载到内存
  2. argv 处理：需要特别留意内核是如何将用户态的参数字符串数组（myargs）拷贝到新进程栈顶的。这是操作系统内核与用户程序交互的关键桥梁

机制：受限直接执行 ​

操作系统通过时分技术共享 CPU，从而实现虚拟化。构建这种机制需要面对两个挑战：

  • 性能：如何在不增加系统开销的情况下实现虚拟化
  • 控制权：如何有效的运行进程，同时保留对CPU的控制

直接在CPU上运行程序。os启动程序运行时，在进程列表中创建一个进程条目，分配对应的内存并将程序代码加载到内存，找到入口点，跳转后开始运行，执行完成后回到内核并清除。这样的操作优势是快速，但是也带来了几种问题

假如进程需要执行某种受限操作 ​

如磁盘发出 I/O 请求或获得更多系统资源（如 CPU 或内存），我们引入用户模式，在用户模式下程序执行会受到限制，比如不能发出IO请求。这样做会导致处理器引发异常，操作系统可能会终止进程

操作系统以内核模式运行，可以运行特权操作，比如IO请求

而用户想要运行特权操作，就要使用硬件为用户程序提供的系统调用的能力。执行系统调用时，程序需要执行特殊的陷阱（Trap）指令。该指令同时跳入内核并将特权级别提升到内核模式。完成后操作系统调用一个特殊的从陷阱返回指令，该指令返回到发起调用的用户程序中，同时将特权级别降低，回到用户模式

执行陷阱时，必须确保存储足够的调用者寄存器，以便在操作系统发出从陷阱返回指令时能够正确返回

内核通过在启动时设置陷阱表 trap table 来获取OS内运行的代码。当机器启动时，它在内核模式下执行，因此可以根据需要自由配置机器硬件。操作系统做的第一件事，就是告诉硬件在发生某些异常事件时要运行哪些代码

LDE 协议有两个阶段。第一个阶段在系统引导时，内核初始化陷阱表，并且CPU 记住它的位置以供随后使用。内核通过特权指令来执行此操作。第二个阶段在运行进程时，在使用从陷阱返回指令开始执行进程之前，内核设置了一些内容（例如，在进程列表中分配一个节点，分配内存），这会将CPU 切换到用户模式并开始运行该进程。当进程希望发出系统调用时，它会重新陷入操作系统，然后再次通过从陷阱返回，将控制权还给进程。该进程然后完成它的工作，并从main()返回。这通常会返回到一些存根代码，它将正确退出该程序（例如，通过调用exit()系统调用，这将陷入OS 中）

如何在进程间切换 ​

协作方式：等待系统调用

大多数进程通过进行系统调用，将 CPU 的控制权转移给操作系统。如果应用程序执行了某些非法操作，也会将控制转移给操作系统

非协作方式：操作系统进行控制，进程不协作

操作系统如何获得 CPU 的控制权？操作系统可以做什么来确保流氓进程不会占用机器？

时钟中断。时钟设备可以编程为每隔几毫秒产生一次中断。产生中断时，当前正在运行的进程停止，操作系统中预先配置的中断处理程序会运行。此时操作系统重新获得 CPU 的控制权，因此可以做它要做的事：停止当前进程，并启动另一个进程

  • 操作系统必须通知硬件哪些代码在发生时钟中断时运行
  • 在启动过程中，操作系统也必须启动时钟
  • 硬件要为正在运行的程序保存足够的状态，以便随后从陷阱返回指令并能正确恢复正在运行的程序

保存和恢复上下文

操作系统重获控制权后，应该选择继续运行当前进程，或者切换进程。需要运行调度程序做出决策。如果选择切换需要做出如下的行为：

  • 操作系统要做的就是为当前正在执行的进程保存一些寄存器的值
  • 并为即将执行的进程恢复一些寄存器的值

操作系统会执行一些底层汇编代码，来保存通用寄存器、程序计数器，以及当前正在运行的进程的内核栈指针，然后恢复寄存器、程序计数器，并切换内核栈，供即将运行的进程使用。通过切换栈，内核在进入切换代码调用时，是一个被中断的进程的上下文，在返回时，是另一即将执行的进程的上下文。当操作系统最终执行从陷阱返回指令时，即将执行的进程变成了当前运行的进程

在此协议中，有两种类型的寄存器保存/恢复。第一种是发生时钟中断的时候。在这种情况下，运行进程的用户寄存器由硬件隐式保存，使用该进程的内核栈。第二种是当操作系统决定从 A 切换到 B。在这种情况下，内核寄存器被操作系统明确地保存，但这次被存储在该进程的进程结构的内存中。后一个操作让系统从好像刚刚由 A 陷入内核，变成好像刚刚由 B 陷入内核

进程调度：介绍 ​

本节的首要关注点是周转时间：T 周转时间 = T 完成时间 −T 到达时间

先进先出 FIFO ​

先进先出调度，有时候也称为先到先服务

  • 缺点：一些耗时较少的潜在资源消费者被排在重量级的资源消费者之后

最短任务优先 SJF ​

先运行最短的任务，然后是次短的任务

最短完成时间优先 STCF ​

向 SJF 添加抢占，称为最短完成时间优先或抢占式最短作业优先调度程序

每当新工作进入系统时，它就会确定剩余工作和新工作中，谁的剩余时间最少，然后调度该工作

轮转 RR ​

新度量指标，响应时间：T 响应时间 = T 首次运行 −T 到达时间

响应时间定义为从任务到达系统到首次运行的时间。为了用户与系统有更好的交互性，引入了分时系统。例如，如果 3 个工作同时到达，第三个工作必须等待前两个工作全部运行后才能运行。轮转负责解决这个问题

RR 在一个时间片内运行一个工作，然后切换到运行队列中的下一个任务，而不是运行一个任务直到结束。反复执行直到所有任务完成。时间片长度必须是时钟中断周期的倍数

假设 3 个任务 A、B 和 C 在系统中同时到达，并且它们都希望运行5s。SJF 调度程序必须运行完当前任务才可运行下一个任务。相比之下，1s 时间片的 RR 可以快要地循环工作

RR 的平均响应时间是：（0 + 1 + 2）/3 = 1; SJF 算法平均响应时间是：（0 + 5 + 10）/ 3 = 5

如果时间片太短又会导致上下文切换的开销。需要权衡时间片长度来摊销上下文切换成本。而对于周转时间，只关心作业何时完成。ABC每个运行时间为 5s，RR 是拥有1s 时间片的调度程序。A 在 13 完成，B 在14，C 在 15，平均 14。RR 几乎是最差的，在很多情况下甚至比简单的 FIFO 更差

任何公平的策略如 RR，即在小规模的时间内将 CPU 均匀分配到活动进程之间，在周转时间这类指标上表现不佳

我们开发了两种调度程序。第一种类型（SJF、STCF）优化周转时间，但对响应时间不利。第二种类型（RR）优化响应时间，但对周转时间不利。我们还有两个假设需要放宽：假设 4（作业没有 I/O）和假设 5（每个作业的运行时间是已知的）

结合 I/O ​

当程序执行 I/O，期间不会使用 CPU，它被阻塞等待 I/O 完成。这时调度程序应该在 CPU上安排另一项工作，且必须在 I/O 完成时做出决定。发生这种情况时会产生中断，操作系统运行并将发出 I/O 的进程从阻塞状态移回就绪状态。操作系统应该如何处理每项工作？

假设工作 A 和 B，每项需要 50ms 的 CPU时间。A 运行 10ms，然后发出 I/O 请求（假设 I/O 每个都需要10ms），而 B 只是使用 CPU 50ms，不执行 I/O。调度程序先运行 A，然后运行 B

一种常见的方法是将 A 的每个 10ms 的子工作视为一项独立的工作。当系统启动时，它的选择是调度 10ms 的 A，还是 50ms 的 B。对于 STCF，选择较短的一个，这种情况下是 A。A 的工作完成， B开始运行。然后提交 A的一个新子工作，它抢占 B 并运行 10ms。这样做可以实现重叠，一个进程在等待另一个进程的 I/O 完成时使用 CPU，系统因此得到更好的利用

这样我们就看到了调度程序可能如何结合 I/O。通过将每个 CPU 突发作为一项工作，调度程序确保“交互”的进程经常运行。当这些交互式作业正在执行 I/O 时，其他 CPU 密集型作业将运行，从而更好地利用处理器

假设5无法预知，就不过多赘述了

调度 ：多级反馈队列 MLFQ ​

多级反馈队列优化了周转时间和响应时间

规则1：MLFQ存在多个队列，每个队列有不同优先级，一个工作只能存在于一个队列中

规则2：MLFQ总是执行优先级较高的工作。对于相同优先级的工作采取轮转调度

如何改变优先级 ​

  • 规则 3：工作进入系统时，放在最高优先级（最上层队列）
  • 规则 4a：工作用完整个时间片后，降低其优先级（移入下一个队列）
  • 规则 4b：如果工作在其时间片以内主动释放 CPU，则优先级不变

实例 1：单个长工作

  • 新工作进入最高优先级队列 (Q2)，若在该队列的一个时间片内未完成，优先级减 1 (Q1)。若在 Q1 时间片内仍未完成，继续降级至最低优先级 (Q0)，CPU 密集型长任务最终会驻留在底层队列，以轮转调度RR方式运行

实例 2：短任务插入

  • 系统已有长任务在底层运行，此时一个新的短任务到达。MLFQ 假设所有新任务都是短任务，直接赋予最高优先级，短任务抢占 CPU 运行。如果它在时间片用完前执行完毕，它就不会被降级，实现了类似 SJF 最短任务优先的效果，保证了短任务的快速周转，而无需预知任务时长

实例 3：I/O 密集型工作

  • 如果进程在时间片用完前主动放弃 CPU (例如进行 I/O 等待)，保持其优先级不变。交互式作业（如等待键盘输入）通常运行时间极短但频繁。此规则确保它们维持在最高优先级，从而保证系统的响应能力

上述简单规则构建的 MLFQ 存在严重的漏洞，主要体现在公平性和安全性上

缺陷 1：饥饿

如果系统中有大量的交互式短任务不断地占用最高优先级队列，最低优先级队列中的长任务将无法获得任何 CPU 时间，长任务被饿死

缺陷 2：愚弄/欺骗调度程序

利用“主动放弃 CPU 则保持优先级”的规则。程序在时间片即将用完前（例如运行 99% 时），发出一个无意义的 I/O 请求主动放弃 CPU。该程序的计时器重置，重新运行后仍处于最高优先级。通过这种方式，CPU 密集型任务可以欺骗系统，长期独占高优先级资源，破坏公平性

缺陷 3：缺乏适应性

一个进程的性质可能会随时间改变（例如一个程序在计算密集阶段结束后，转变为交互式等待用户输入）。在当前规则下，一旦该进程被降级到最低队列，它就很难再回到高优先级队列，即使它变成了交互式作业

提升优先级 ​

  • 规则 5：经过一段时间 S，就将系统中所有工作重新加入最高优先级队列

通过周期性的提升所有工作的优先级，让CPU密集型工作也能更多的进行，避免饥饿。如果一个 CPU 密集型工作变成了交互型，通过提升优先级，调度器能重新将其识别为高优先级任务，恢复响应速度

但是时间段的设置非常关键且困难，太长长任务依然会饥饿，太短交互型任务无法获得足够的 CPU 比例

更好的计时方式 ​

规则 4：一旦工作用完了其在某一层中的时间配额（无论中间主动放弃了多少次CPU），就降低其优先级

为了防止恶意程序通过在时间片结束前主动放弃 CPU（如发出微小的 I/O 请求）来重置计时器并长期霸占高优先级队列，必须修改计时逻辑。调度器记录进程在当前队列中消耗的累积总时间，不关心进程是一次用完还是分多次用完，一旦累积时间达到配额，立即降级。彻底杜绝了通过 I/O 欺骗调度器的行为，实现了公平的降级

MLFQ 的参数调优 ​

MLFQ 不仅仅是规则，还涉及大量参数配置，这些配置通常写在配置文件或内核表中

  • 队列的数量
  • 每一层队列的时间片长度
  • 优先级提升的时间间隔 ()
  • 可变时间片：大多数 MLFQ 变体对不同优先级的队列采用不同的时间片长度
    • 高优先级：短时间片（如 10ms），用于快速响应交互
    • 低优先级：长时间片（如几百 ms），用于提高 CPU 密集型任务的吞吐量，减少上下文切换开销

实例：

  • Solaris：使用表格配置 60 个队列，时间片从 20ms 到几百 ms 不等，约 1秒提升一次优先级
  • FreeBSD：使用数学公式计算优先级，配合使用量衰减 (Decay-usage) 算法，而非简单的表格或规则
  • 用户干预：大多数系统提供 nice 命令，允许用户手动调整进程优先级建议

总结 ​

  • 规则 1：如果 A 的优先级 > B 的优先级，运行 A（不运行 B）
  • 规则 2：如果 A 的优先级 = B 的优先级，轮转运行 A 和 B
  • 规则 3：工作进入系统时，放在最高优先级（最上层队列）
  • 规则 4：一旦工作用完了其在某一层中的时间配额（无论中间主动放弃了多少次CPU），就降低其优先级
  • 规则 5：经过一段时间 S，就将系统中所有工作重新加入最高优先级队列

调度：比例份额 ​

该调度策略目的是确保每个工作获得一定比例的 CPU 时间，而非追求优化周转时间或响应时间

彩票机制 ​

利用随机性来实现比例分配。每隔一个时间片，调度器举行一次抽奖，中奖的进程获得运行机会

随机性的优势

  1. 避免边角情况：随机算法通常没有特定的“最差情况”
  2. 轻量：几乎不需要记录状态（只需知道彩票数），不需要复杂的计时
  3. 快速：生成随机数很快，决策过程迅速

实现逻辑

  1. 生成随机数 winner (范围：0 到 total_tickets - 1)
  2. 遍历进程列表，累加彩票数 counter
  3. 当 counter > winner 时，当前列表项对应的进程即为中奖者
  • 优化：将列表按彩票数递减排序，可减少遍历次数，提高查找效率

辅助机制 ​

  1. 彩票货币

用户可以拥有一套自己的货币体系分配给子任务，操作系统负责将其兑换为全局彩票。

  • 例子：用户 A 有 100 张全局彩票，分给两个子进程各 500 张“A币”。OS 会自动按比例（500 A币 = 50 全局票）进行转换
  1. 彩票转让

进程可以将彩票临时转让给另一个进程

  • 场景：客户端转让彩票给服务端，加速服务端处理自己的请求
  1. 彩票通胀

进程自主增加自己的彩票数

  • 前提：仅适用于进程间互相信任的环境（非竞争环境），否则会被恶意利用独占 CPU

问题 ​

  • 短期不公平：随机性导致短期内无法严格保证比例
  • 当任务运行时间很短时，不公平度较高
  • 只有运行时间足够长，比例才会趋近于期望值（大数定律）

对比彩票调度 ​

  • 优点：在每个调度周期结束后，都能精确地按照票数比例分配 CPU
  • 缺点：全局状态问题
  • 新进程加入时，Pass 值设为多少？
  • 设为 0 新进程会长期垄断 CPU 直到追上其他进程
  • 彩票调度无此问题，新进程只需更新总票数即可，融入系统更平滑

步长调度 ​

为了解决彩票调度因随机性导致的短期不公平问题，Waldspurger 提出了一种确定性的算法

该算法维护两个关键变量：

  • 步长：与进程的票数成反比，票数越多，步长越小（意味着走得慢，更容易被再次选中）
  • 行程值：进程当前的累积进度计数器

调度算法逻辑

  1. 选择：从队列中选择当前行程值最小的进程运行
  2. 执行：运行该进程一个时间片
  3. 更新：更新该进程的行程值：
  4. 循环：回到步骤 1

在书中的例子中（A=100票, B=50票, C=250票），通过计算步长（A=100, B=200, C=40）调度器会频繁选择步长最小的 C（每 40 累加一次），较少选择 B（每 200 累加一次）。在一段周期结束后，C 运行 5 次，A 运行 2 次，B 运行 1 次。这精确匹配了票数比例 (250: 100: 50 = 5: 2: 1)。彩票调度依靠概率长期收敛，而步长调度在每个周期都能保证完全正确的比例

步长调度的缺陷：新进程接入问题

  • 问题：当一个新的进程加入系统时，它的 Pass 值该设为多少？
  • 设为 0：如果其他进程的 Pass 已经很大（例如 10000），新进程（Pass=0）会拥有绝对的最小行程值，从而独占 CPU 直到追上其他进程
  • 设为当前最小值：虽然可行，但实现起来需要维护全局状态，增加了复杂性

彩票调度的优势：无状态

  • 灵活性：彩票调度不需要记录每个进程的历史（行程值）
  • 动态性：新进程加入时，只需要更新总票数即可。新进程立即根据其持有的彩票数量获得对应的概率，无需担心“追赶”旧进程的问题

多处理器调度 ​

多核环境下需要面对的三个硬件与软件挑战

多处理器架构 ​

单核 CPU 利用缓存Cache加速内存访问，依赖于时间局部性和空间局部性

但在多核系统中，这引发了一致性问题：

  1. CPU 1 读取内存地址 A（值为 D1），放入自己的缓存
  2. CPU 1 修改地址 A 的值为 D2，更新了自己的缓存（尚未写回内存）
  3. 操作系统调度程序将该进程迁移到 CPU 2
  4. CPU 2 读取地址 A。由于其缓存未命中，且内存中的值仍为 D，CPU 2 读到了旧值 D
  • 解决方案：硬件层面的缓存一致性协议，硬件会监控总线上的内存访问。如果 CPU 2 试图读取 A，CPU 1 会检测到，并负责提供最新数据 D2，或者作废 CPU 2 的旧副本

同步 ​

硬件保证了缓存一致性，软件层面（OS内核或应用程序）仍需处理并发访问共享数据的问题

  • 多核同时操作共享数据结构会导致竞态条件。比如两个 CPU 同时尝试 List_Pop，可能导致同一个节点被释放两次，或者数据损坏
  • 解决方案：使用互斥锁（Mutex）保护临界区，保证操作的原子性。但是随着 CPU 核心数增加，锁竞争会严重降低性能

缓存亲和度 ​

这是多处理器调度特有的性能指标。进程在某个 CPU 上运行时，会在该 CPU 的缓存中积累大量热数据。如果下次调度仍在同一个 CPU上运行，缓存命中率高，速度快。如果调度到不同的 CPU上运行，旧缓存失效，新 CPU 需要从内存重新加载数据，速度慢。调度器应尽可能让进程在同一个 CPU上运行，以利用缓存热度

单队列调度 SQMS ​

复用单处理器调度的架构，将所有待调度的工作放入一个全局共享队列中。所有的 CPU 从这个队列中取出工作执行。优点是简单，不需要修改现有的调度策略（如 MLFQ），只需让多个 CPU 共享数据结构即可。同时缺陷也不可避免：

  1. 缺乏可扩展性：为了保证原子性，访问全局队列必须加锁。随着 CPU 数量增加，锁的竞争加剧。CPU 花费大量时间等待锁，导致性能大幅下降
  2. 缓存亲和度差：由于每个 CPU 都是从同一个队列取任务，同一个任务可能时间片在CPU0 上运行，在被调度到 CPU 1 上运行。任务在不同 CPU 间频繁迁移，导致刚预热好的缓存失效，必须频繁从内存重新加载数据，降低执行效率

改进尝试：亲和度机制，修改 SQMS，使其在调度时尽可能让进程回到上一次运行的 CPU。但这会增加实现的复杂性，且可能损害负载均衡

多队列多处理器调度 MQMS ​

每个 CPU 拥有自己独立的调度队列。当新工作进入系统时，根据某种启发式规则（如随机、轮询或选择最空闲的队列）将其放入某个 CPU 的队列。每个 CPU 独立调度自己队列中的工作，互不干扰

  1. 可扩展性好：队列私有化消除了全局锁。CPU 访问本地队列无需竞争全局锁，随着核数增加，开销不会显著增长
  2. 良好的缓存亲和度：工作一旦分配给某个 CPU，默认情况下会一直留在该 CPU 的队列中。这最大化了缓存命中的几率

新问题：负载不均

由于队列间相互独立，可能出现工作分配不均的情况：

  • 情形 A（空闲）：CPU 0 有 0 个任务，CPU 1 有 2 个任务。CPU 0 空转，资源浪费
  • 情形 B（不公平）：CPU 0 有 1 个任务（获得 100% CPU），CPU 1 有 2 个任务（各获得 50% CPU）。虽然都在工作，但对任务本身不公平

解决负载不均：迁移

为了解决 MQMS 的负载不均，必须允许工作在不同 CPU 的队列之间移动，称为迁移

工作窃取机制：工作量较少或空闲的队列定期检查其他队列。如果发现目标队列比自己更忙，就从目标队列“窃取”一个或多个工作

  • 检查太频繁：带来高昂的开销（如破坏缓存、锁竞争），降低系统整体效率
  • 检查太少：无法及时解决负载不均，导致资源浪费或不公平
  • 策略：必须找到合适的检查间隔阈值（这也是系统调优的难点）

Linux 多处理器调度 ​

在构建多处理器调度程序方面，Linux 社区一直没有达成共识。一直以来，存在 3 种不同的调度程序：O(1)调度程序、完全公平调度程序（CFS）以及 BF 调度程序（BFS）

O(1) CFS 采用多队列，而 BFS 采用单队列，这说明两种方法都可以成功。当然它们之间还有很多不同的细节。例如，O(1)调度程序是基于优先级的（类似于之前介绍的 MLFQ），随时间推移改变进程的优先级，然后调度最高优先级进程，来实现各种调度目标。交互性得到了特别关注。与之不同，CFS 是确定的比例调度方法（类似之前介绍的步长调度）。BFS作为三个算法中唯一采用单队列的算法，也基于比例调度，但采用了更复杂的方案，称为最早最合适虚拟截止时间优先算法（EEVEF）
