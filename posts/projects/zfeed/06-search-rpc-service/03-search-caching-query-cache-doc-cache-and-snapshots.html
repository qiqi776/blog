搜索缓存：查询缓存、文档缓存与快照 ​

Search RPC 服务实现了一套多层缓存策略，用于提供稳定分页、降低高频搜索下的数据库负载，并保证热门查询的性能稳定。该系统区分短期查询结果缓存和长期稳定搜索快照。

两层 Redis 缓存架构 ​

缓存系统分为两个逻辑层：查询快照缓存（页面级）和文档摘要缓存（实体级）。

1. 查询快照缓存（页面级） ​

这一层会缓存特定搜索查询、模式和页码对应的 ID 列表及基础元数据。app/rpc/search/internal/logic/cache.go#19 它用于快速返回热门关键词的前几页搜索结果。

  • Key 结构：search:cache:q:{version}:{entity}:{mode}:{query_hash}:{page}。app/rpc/search/internal/logic/cache.go#91
  • 版本控制：使用 searchQueryCacheVersion = 1，方便缓存对象结构迁移。app/rpc/search/internal/logic/cache.go#22
  • TTL 抖动：为防止大量缓存 key 同时过期导致“惊群”，TTL 会在 30 到 90 秒之间抖动。app/rpc/search/internal/logic/cache.go#25-28

2. 文档摘要缓存（实体级） ​

这一层存储单个用户或内容项补全后的数据。app/rpc/search/internal/logic/cache.go#20 查询快照缓存保存结果的“顺序”，而文档摘要缓存保存这些结果的“内容”。

  • TTL：比查询缓存更长，通常围绕 600 秒进行抖动。app/rpc/search/internal/logic/cache.go#30-33

数据实体包括：

  • searchCachedUserDoc：存储 UserID、Nickname、Avatar 和 Bio。app/rpc/search/internal/logic/cache.go#53-61
  • searchCachedContentDoc：存储 ContentID、AuthorName、Title、CoverURL 和分数。app/rpc/search/internal/logic/cache.go#63-77

分布式锁与缓存击穿防护 ​

为了防止同一个搜索查询的多个并发请求同时打到数据库（缓存击穿），系统使用 redislock.NewRedisLock。app/rpc/search/internal/logic/cache.go#195-196

  • 锁 key：由查询缓存 key 派生，并追加 :lock 后缀。app/rpc/search/internal/logic/cache.go#345
  • 等待机制：如果某个进程未能获取锁，会进入 waitUserQueryCache（或 waitContentQueryCache），短时间轮询 Redis，查看并发进程是否已完成缓存填充。app/rpc/search/internal/logic/cache.go#205-207
  • 回退：如果无法获取锁且等待超时，系统会直接回退到数据库查询，以保证可用性。app/rpc/search/internal/logic/cache.go#208-209

从缓存模拟 cursor 分页 ​

搜索系统的一个独特能力是从第 0 页缓存中模拟基于 cursor 的分页。如果请求携带 cursor > 0，系统会检查该 cursor 对应的结果是否已经包含在缓存的“第 0 页”中，也就是最常见的搜索入口结果。app/rpc/search/internal/logic/searchcontentslogic.go#67-73

  • 逻辑：cachedContentsAfterCursor 加载第一页缓存。app/rpc/search/internal/logic/cache.go#168-170
  • 偏移计算：查找 cursor 在缓存列表中的索引。app/rpc/search/internal/logic/cache.go#178
  • 子切片：如果找到 cursor 且后续剩余条目足够，则返回从该 cursor 之后开始的缓存结果切片。app/rpc/search/internal/logic/cache.go#183-184

用于稳定分页的搜索快照 ​

标准缓存用于提升性能，而快照用于保证一致性。当 SearchSnapshotEnabled 为 true 时，app/rpc/search/internal/config/config.go#14 系统会为用户的搜索会话捕获一组固定结果。

快照生命周期 ​

  1. 创建：在第一页（offset 0）时，系统向后端查询一大批结果（最多 SEARCH_SNAPSHOT_MAX_ITEMS，默认 100）。app/rpc/search/internal/logic/searchcontentslogic.go#224-233
  2. 持久化：该批结果会以“Snapshot” 形式保存到 Redis，并拥有唯一 ID。app/rpc/search/internal/logic/snapshot.go#101-105
  3. 消费：后续请求提供 PageToken，其中包含 SnapshotID 和当前 Offset。app/rpc/search/internal/logic/searchcontentslogic.go#166
  4. 过期：快照生命周期很短（默认 60 秒），避免占用过多内存。deploy/.env#30

配置参数 ​

缓存行为由环境变量和 Config 结构体控制。app/rpc/search/internal/config/config.go#8-22

变量配置字段说明
SEARCH_CACHE_ENABLEDSearchCacheEnabled查询/文档缓存的总开关。
SEARCH_SNAPSHOT_ENABLEDSearchSnapshotEnabled稳定快照分页开关。
SEARCH_QUERY_CACHE_TTL_SECONDSSearchQueryCacheTTLSeconds查询页面结果的基础 TTL。
SEARCH_DOC_CACHE_TTL_SECONDSSearchDocCacheTTLSeconds实体摘要的基础 TTL。
SEARCH_QUERY_CACHE_MAX_PAGESSearchQueryCacheMaxPages最大缓存页深度，通常为 3-5。
SEARCH_SNAPSHOT_MAX_ITEMSSearchSnapshotMaxItems单个快照捕获的最大结果数。
