搜索后端与查询归一化 ​

search-rpc 服务使用多层搜索策略，当前主要由 MySQL 支撑。它引入查询归一化以保证缓存一致性，并使用 MySQL Full-Text Search（FTS）能力；如果 FTS 没有结果或不可用，则回退到 LIKE 模式，以提升兼容性和可靠性。

查询归一化 ​

在任何搜索落到数据库或缓存之前，原始输入字符串都会先由 DefaultNormalizer 处理。这样可以避免用户输入中的细微差异（例如额外空格、大小写差异）生成冗余缓存条目或不一致的搜索结果。

归一化流程 ​

  1. 裁剪：移除首尾空白。app/rpc/search/internal/querynorm/normalizer.go#35
  2. 规范化：将字符串转换为小写，并把内部连续空白折叠为单个空格。app/rpc/search/internal/querynorm/normalizer.go#36
  3. 哈希：基于规范化字符串生成短 SHA-256 哈希（前 8 字节），作为缓存 key 标识符。app/rpc/search/internal/querynorm/normalizer.go#45 app/rpc/search/internal/querynorm/normalizer.go#50-53
  4. 日志脱敏：为保护用户隐私（例如搜索手机号），包含 7 个或更多数字的查询会在日志中被掩码为 [numeric-query]。app/rpc/search/internal/querynorm/normalizer.go#55-66

数据结构：querynorm.Query ​

字段说明
Raw用户输入的原始字符串。
SearchText裁剪后的输入，用于数据库查询。
Canonical小写且空白折叠后的版本，用于哈希。
Hash16 字符十六进制字符串，用于 Redis key。

来源：app/rpc/search/internal/querynorm/normalizer.go#12-48

搜索后端抽象 ​

系统使用 Factory 模式管理搜索后端。虽然当前实现主要使用 MySQL，但架构被设计为支持未来的搜索引擎（代码中称为 engine）。

Backend Factory 逻辑 ​

backend.Factory 根据配置决定使用哪种实现。

  • 配置后端：通过环境变量/配置设置，例如 mysql 或 engine。app/rpc/search/internal/backend/backend.go#45-57
  • 有效后端：如果配置为 engine 但尚未实现，则默认使用 mysql。app/rpc/search/internal/backend/backend.go#47-50

MySQL 全文搜索与计分 ​

searchRepositoryImpl 实现两阶段搜索：先尝试高性能全文搜索，如果 FTS 返回空结果或不可用，则回退到标准 LIKE 查询。app/rpc/search/internal/repositories/search_repository.go#90-119

用户搜索 ​

用户搜索面向 nickname、bio 和 mobile 列。app/rpc/search/internal/repositories/search_repository.go#132

  • Boolean Mode：归一化器会将查询转换为兼容 boolean mode 的字符串，例如添加 * 以支持前缀匹配。app/rpc/search/internal/repositories/search_repository.go#123-132
  • 回退：如果 FTS 失败，则在相同字段上使用 %query% LIKE 模式。app/rpc/search/internal/repositories/search_repository.go#100-105

内容搜索与计分 ​

内容搜索更复杂，会联接 zfeed_content、zfeed_article 和 zfeed_video。app/rpc/search/internal/repositories/search_repository.go#193-223 它会计算三类分数来确定相关性：

分数类型计算逻辑
Text Score查询精确匹配标题时提升 30 分，以标题开头时提升 20 分，出现在标题中时提升 10 分；描述匹配获得较低提升 5 分。app/rpc/search/internal/repositories/search_repository.go#204-210
Hot Score直接来自 zfeed_content 的 hot_score 列，表示历史互动热度。app/rpc/search/internal/repositories/search_repository.go#203
Rank ScoreText Score 与 Hot Score 之和，用于 “Relevance” 和 “Hybrid” 搜索模式。app/rpc/search/internal/repositories/search_repository.go#211-217

搜索模式 ​

系统通过 mode 参数支持不同排序策略。app/rpc/search/internal/repositories/search_repository.go#171

  1. Latest：按 published_at DESC 排序。
  2. Relevance：按 rank_score DESC 排序。
  3. Hybrid：相关性与热度的加权组合（具体实现随 repository 方法而定）。

分页与元信息 ​

搜索结果会携带 SearchMeta，用于指示内部实际采用的数据读取路径，例如 fulltext、like 或 none。app/rpc/search/internal/repositories/search_repository.go#26-29

分页通过 cursor 处理，通常是上一页最后一项的 ID，用于在新内容持续发布时维持较稳定的结果。app/rpc/search/internal/repositories/search_repository.go#107-111 app/rpc/search/internal/repositories/search_repository.go#134-137
