interaction-rpc 中的点赞与取消点赞系统，为用户对内容（文章、视频）和评论的互动提供高性能、最终一致的机制。它采用多层方案：使用 Redis 完成低延迟的原子状态转换，通过 Transactional Outbox 可靠投递事件，并使用带版本字段的幂等数据库更新处理乱序消息。

系统架构与数据流 ​

系统分为写路径（Request -> Cache -> Outbox）和后台 relay 路径（Outbox -> Kafka -> Consumer -> DB）。

核心实现细节 ​

原子状态转换（Redis Lua） ​

为了保证高并发安全并避免竞态条件（例如快速连续点击两次点赞），系统使用 Redis Lua 脚本。用户点赞状态存储在一个 Hash 中，其中 field 由 scene 和 content ID 组合而成：[scene:content_id]。

  • 点赞脚本：将 field 设置为 "1"。只有当原状态不是 "1" 时，才返回 changed=1。app/rpc/interaction/internal/common/utils/lua/like_user_hash.lua#19-30
  • 取消点赞脚本：将 field 设置为 "0"。当原状态是 "1" 时，返回 changed=1。app/rpc/interaction/internal/common/utils/lua/cancel_like_user_hash.lua#16-18

Transactional Outbox 与回滚 ​

当 Redis 中检测到状态变更后，服务会尝试把事件持久化到 zfeed_like_event_outbox 表。如果事件发布失败（例如数据库错误），系统会回滚缓存，使 Redis 状态与上一次已知的持久化状态保持一致。app/rpc/interaction/internal/logic/like/likelogic.go#57-60

缓存缺失时回退数据库 ​

如果用户的点赞状态在 Redis 中缺失（例如缓存过期），系统会回退到 MySQL 数据库判断当前状态，然后再更新缓存。app/rpc/interaction/internal/logic/like/unlikelogic.go#94-104

带版本字段的幂等 Upsert ​

为了处理 Kafka 消息重投递或事件乱序，Upsert 逻辑使用 last_event_ts（版本字段）。只有当传入事件时间戳大于或等于数据库中当前保存的时间戳时，状态才会更新。

sql
INSERT INTO zfeed_like (
  user_id, scene, content_id, status, last_event_ts, ...
)
VALUES (?, ?, ?, ?, ?, ...)
ON DUPLICATE KEY UPDATE
  status = IF(VALUES(last_event_ts) >= last_event_ts, VALUES(status), status),
  last_event_ts = GREATEST(last_event_ts, VALUES(last_event_ts)),
  updated_at = IF(VALUES(last_event_ts) >= last_event_ts, CURRENT_TIMESTAMP, updated_at)
