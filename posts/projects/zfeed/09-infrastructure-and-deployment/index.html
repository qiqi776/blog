本页从高层介绍 zfeed 的基础设施栈、部署编排，以及支撑微服务生态的运维组件。系统设计为完全容器化且可观测，使用现代云原生栈来处理消息通信、服务发现和数据一致性。

部署栈与编排 ​

整个 zfeed 环境使用 Docker Compose 编排，负责管理 6 个后端服务及其支撑基础设施的生命周期。该栈设计为通过统一启动脚本完成一键部署 scripts/start.sh#14-17

服务拓扑 ​

部署被划分为三个逻辑层：

  1. 网关层：Nginx 作为反向代理，处理 SSL 终止（可选）和 request ID 注入 deploy/nginx/default.conf#1-4，并将流量转发到 front-api deploy/nginx/default.conf#57-70
  2. 应用层：6 个基于 go-zero 的服务（front-api、user-rpc、content-rpc、interaction-rpc、count-rpc、search-rpc）运行在隔离容器中 deploy/docker-compose.yml#1-36
  3. 基础设施层：包含 MySQL、Redis、Kafka、Etcd 和 Canal 等状态与协调服务 deploy/docker-compose.yml#40-150

数据库与 Schema 管理 ​

zfeed 使用 MySQL 作为事实来源。Schema 管理通过 scripts/sql/ 中的 SQL 脚本完成 deploy/docker-compose.yml#93，这些脚本会在容器初始化期间通过自定义 reseed 脚本自动应用 deploy/docker-compose.yml#95

系统使用多个领域专属表，例如 zfeed_user、zfeed_content 和 zfeed_count_value。可靠事件投递则通过 zfeed_like_event_outbox 等 outbox 表管理。

表结构和索引详情请参见 数据库 Schema 与迁移。

可观测性流水线 ​

可观测性栈通过三大支柱深入呈现系统健康状况：

  1. 指标：Prometheus 抓取每个服务的 exporter 端口，例如 9290 到 9295 deploy/prometheus/prometheus.yml#9-37
  2. 追踪：OpenTelemetry（OTEL）collector 将 trace 转发到 Jaeger，用于分布式请求可视化 deploy/docker-compose.yml#167-189
  3. 日志：go-zero 生成结构化日志，包括 access、error、slow、stat，可通过 Filebeat/Logstash 流水线收集 README.md#59-62

指标与追踪配置详情请参见 可观测性：指标、追踪与日志。

CDC 与消息基础设施 ​

为了将高频计数和社交互动与核心业务逻辑解耦，zfeed 使用 Change Data Capture（CDC）。Canal 监听 MySQL binlog 并将变更流式写入 Kafka deploy/docker-compose.yml#133-150。这使 count-rpc 服务可以异步更新计数器，而不会影响主要写操作的延迟。

Canal 到 Kafka 的流水线以及 Transactional Outbox 模式详情，请参见 Canal CDC 与 Kafka 消息。
