zfeed 系统基于 go-zero 框架构建，采用微服务架构。它把内容社区平台拆分为六个专门服务，这些服务通过高性能 gRPC 交互，使用 Etcd 做服务发现，并依赖一组基础设施组件完成数据持久化、缓存和事件驱动处理。

微服务拓扑 ​

系统包含一个统一入口 API 网关和五个后端 RPC 服务。服务间通信严格基于 gRPC，网关则向客户端暴露 RESTful HTTP 接口。

服务概览 ​

服务职责端口
front-apiHTTP 入口、认证、请求聚合。5000
user-rpc用户生命周期、会话管理和个人资料数据。5003
content-rpc内容发布、Feed 生成和热门内容排序。5001
interaction-rpc社交动作（点赞、评论、关注）和事件 outbox。5002
count-rpc高频计数器管理和 CDC 事件消费。5004
search-rpc面向用户和内容的全文搜索，并提供稳定分页。5006

来源：README.md#23-30 deploy/.env#19-25

服务通信与发现 ​

所有 RPC 服务都会注册到 Etcd。客户端（包括 front-api 和其他 RPC 服务）使用 Etcd 作为服务发现后端，动态定位目标服务实例。

  • 注册：服务将自己的监听地址（例如 CONTENT_RPC_LISTEN_ON）注册到 Etcd 中的特定 key 下，例如 content.rpc。app/rpc/search/etc/search.yaml#33-36 deploy/.env#21-25
  • 发现：客户端配置中定义 Etcd 主机和 key，用于动态解析服务端点。app/rpc/search/etc/search.yaml#38-43
  • 服务间调用：服务经常相互调用以聚合数据。例如 content-rpc 的 GetContentDetail 会并发调用 user-rpc、count-rpc 和 interaction-rpc。app/rpc/content/internal/logic/content/getcontentdetaillogic.go#180-212

技术实现细节 ​

配置管理 ​

服务使用 .yaml 文件，并通过 go-zero 的 conf.Load 支持环境变量展开。这使同一个二进制文件可以在不同环境（Dev、Test、Prod）中借助 deploy/.env 文件加载不同配置。

  • 文件路径：app/rpc/search/etc/search.yaml。app/rpc/search/etc/search.yaml#1-61
  • 测试校验：TestSearchConfigLoadsWithEnv 确保 SEARCH_RPC_LISTEN_ON、MYSQL_HOST 等变量能正确映射到 Config 结构体。app/rpc/search/internal/config/config_env_test.go#9-63

可观测性 ​

系统集成了一整套可观测性能力：

  1. 指标：为搜索延迟、缓存命中率和请求总量定义自定义 Prometheus 直方图与计数器。app/rpc/search/internal/logic/observability.go#29-71
  2. 链路追踪：OpenTelemetry（OTEL）采集器收集所有服务的 trace，并在 Jaeger 中可视化。deploy/.env#51-59
  3. 日志：各服务输出结构化 JSON 日志，并存储在 /var/log/zfeed。app/rpc/search/etc/search.yaml#16-32

搜索架构 ​

search-rpc 服务实现多层缓存策略，用于处理复杂的全文搜索查询：

  • 查询缓存：存储高频关键词的页面级结果。app/rpc/search/internal/config/config.go#13-21
  • 文档缓存：缓存单个实体摘要。app/rpc/search/internal/config/config.go#20
  • 快照系统：通过在 Redis 中按指定 TTL 冻结结果集，提供稳定分页。app/rpc/search/internal/logic/observability.go#139-141
