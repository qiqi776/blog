本文说明 content-rpc 服务中四种主要 Feed 类型的实现。这些系统结合 Redis Sorted Set（ZSet）实现高性能索引，使用 Lua 脚本实现原子分页，并通过补全流水线组装丰富的内容元数据。

Feed 类型概览 ​

系统按照分发模型和可见性规则对 Feed 进行分类：

Feed 类型模型存储实体分页 cursor
推荐（热门）拉取（快照）hot_feed ZSet内容 ID（来自 ZSet score）
关注收件箱推送（Fan-out）follow_inbox:{uid} ZSet内容 ID
用户发布拉取（按需）user_publish:{uid} ZSet内容 ID
用户收藏拉取（按需）user_favorite:{uid} ZSet收藏 ID（来自 ZSet score）

推荐 Feed（热门 Feed） ​

推荐 Feed 提供全局排序的“热门”内容列表。为了保证稳定分页（防止分数变化时内容跨页跳动），它使用快照机制。

实现细节 ​

  • 快照选择：逻辑首先从请求中解析 SnapshotId。app/rpc/content/internal/logic/feed/recommendfeedlogic.go#101-110 如果请求未提供，则使用 hot_feed:latest 中存储的最新全局快照 ID。app/rpc/content/internal/logic/feed/recommendfeedlogic.go#138-140
  • Lua 脚本：使用 QueryHotFeedZSetScript 原子检查快照是否存在，并获取一页 ID。app/rpc/content/internal/logic/feed/recommendfeedlogic.go#133-145
  • 回退：如果请求的快照已经过期，系统会回退到实时的 hot_feed ZSet。app/rpc/content/internal/common/utils/lua/query_hot_feed_zset.lua#1-20

来源：app/rpc/content/internal/logic/feed/recommendfeedlogic.go#48-99 app/rpc/content/internal/logic/feed/recommendfeedlogic_test.go#151-182

关注收件箱（推模型） ​

关注 Feed 使用基于推送的“收件箱”模型：内容发布时，会 fan-out 到粉丝各自的 Redis ZSet 中。

Cache-Aside 与重建 ​

如果用户的 follow_inbox 缓存缺失（例如被淘汰或新登录），系统会触发重建：

  1. 分布式锁：使用 gzredis.NewRedisLock 获取锁，锁 key 为 follow_inbox:lock:{uid}。app/rpc/content/internal/logic/feed/followfeedlogic.go#106-110
  2. 数据读取：系统调用 FollowRpc.ListFollowees，找出用户关注的所有作者。app/rpc/content/internal/logic/feed/followfeedlogic.go#243-260
  3. 数据库获取：从这些作者中读取最新 FeedKeepLatestN 条内容（默认 1000）。app/rpc/content/internal/logic/feed/followfeedlogic.go#229-232
  4. 缓存预热：填充 Redis ZSet，并释放锁。app/rpc/content/internal/logic/feed/followfeedlogic.go#117-121

回填机制 ​

当用户新关注一个作者时，会触发 BackfillFollowInbox 逻辑，将该作者最近发布的内容拉取到关注者收件箱中。app/rpc/content/internal/logic/content/backfillfollowinboxlogic_test.go#22-78

用户发布与收藏 Feed ​

这些 Feed 基于拉取模型，并且与单个用户的动作相关。

用户发布 Feed ​

  • 索引：存储在 user_publish:{uid}。
  • 维护：在 Publish 流程中更新，并在 DeleteContent 期间清理。app/rpc/content/internal/logic/content/deletecontentlogic.go#114
  • 一致性：缓存缺失时，使用类似关注收件箱的“加锁重建”模式。app/rpc/content/internal/logic/feed/userpublishfeedlogic.go#103-146

用户收藏 Feed ​

  • 索引：存储在 user_favorite:{uid}。
  • 计分：不同于其他使用 ContentID 或 Timestamp 作为 ZSet score 的 Feed，该 Feed 使用 FavoriteID 作为 score，确保列表按照用户收藏时间排序。app/rpc/content/internal/logic/feed/userfavoritefeedlogic_test.go#53-55
  • 数据补全：调用 FavoriteRpc.QueryFavoriteList，从 interaction-rpc 服务重建缓存。app/rpc/content/internal/logic/feed/userfavoritefeedlogic.go#221-250

来源：app/rpc/content/internal/logic/feed/userpublishfeedlogic.go#44-84 app/rpc/content/internal/logic/feed/userfavoritefeedlogic.go#35-75

FeedItemBuilder 补全流水线 ​

FeedItemBuilder 是一个共享工具，负责将原始 ID 转换为完整补全的 ContentItem 对象。

补全步骤 ​

  1. 批量加载：从 MySQL（zfeed_content）加载基础内容元数据，并联接具体表（zfeed_article 或 zfeed_video）。app/rpc/content/internal/logic/feed/feeditembuilder.go#50-80
  2. 互动状态：如果提供了 ViewerId，则调用 interaction-rpc（BatchIsLiked）判断当前用户是否点赞了这些内容。app/rpc/content/internal/logic/feed/feeditembuilder_test.go#82-113
  3. Protobuf 映射：将内部模型映射为 contentpb.ContentItem gRPC 消息格式。

删除时的索引清理 ​

通过 DeleteContentLogic 删除内容时，系统会执行多索引清理，确保该内容立即从所有 Feed 中消失。

清理例程（cleanupIndexes） ​

cleanupIndexes 函数执行以下操作：app/rpc/content/internal/logic/content/deletecontentlogic.go#108-118

  1. 用户发布 Feed：从作者的发布 ZSet 中移除。
  2. 关注收件箱：查询作者粉丝，并从每个粉丝的 Redis 收件箱中移除该 ID。app/rpc/content/internal/logic/content/deletecontentlogic.go#120-142
  3. 收藏 Feed：查询收藏过该内容的用户，并从他们的收藏 ZSet 中移除。app/rpc/content/internal/logic/content/deletecontentlogic.go#148-170
  4. 热门索引：从实时热门 Feed 和当前活跃快照中移除。app/rpc/content/internal/logic/content/deletecontentlogic.go#172-186
