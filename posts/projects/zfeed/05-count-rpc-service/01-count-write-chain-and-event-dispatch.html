Count 写链路与事件分发 ​

count-rpc 服务实现了一个高性能异步计数系统。zfeed 不会在用户动作过程中同步更新计数器，因为那会引入额外延迟和数据库竞争；它通过 Canal 监听 MySQL binlog 实现 CDC（Change Data Capture）。本文说明写链路：从初始数据库变更，到分片计数递增和缓存失效。

架构概览 ​

Count 写链路是一条事件驱动流水线，用于保障社交指标（点赞、评论、收藏、关注）的最终一致性。

数据流：从 MySQL 到计数存储 ​

  1. 源变更：用户执行动作（例如点赞内容），向 zfeed_like 插入一行数据。app/rpc/count/internal/event/strategy/like_strategy.go#13
  2. Canal 捕获：Canal 监听 MySQL binlog（配置为 ROW 格式），deploy/mysql/my.cnf#4-5 并过滤相关互动表。deploy/canal/conf/count/instance.properties#18
  3. Kafka 分发：Canal 将变更事件发布到 zfeed-count-canal Kafka topic。deploy/canal/conf/count/instance.properties#20
  4. Dispatcher 处理：Dispatcher 消费事件、做幂等去重，并路由到 TableStrategy。app/rpc/count/internal/event/dispatcher.go#46-50
  5. 原子更新：CountOperator 将 delta 应用到 zfeed_count_value 表。app/rpc/count/internal/event/dispatcher.go#78-86
  6. 热度计分：如果目标是内容项，Dispatcher 会更新分片 Redis bucket，以影响热门 Feed 排序。app/rpc/count/internal/event/dispatcher.go#124-154

事件分发与策略 ​

Dispatcher 是传入 binlog 事件的中心协调器。它使用策略模式处理不同表结构，避免主分发逻辑过度膨胀。

Dispatcher 逻辑 ​

Dispatcher.Dispatch 函数执行以下步骤：

  1. 策略查找：根据 ChangeEvent 中的表名获取对应 TableStrategy。app/rpc/count/internal/event/dispatcher.go#47-50
  2. 更新提取：策略解析 Current 和 Previous 数据 map，以确定计数 delta（例如 INSERT 为 +1，DELETE 为 -1）。app/rpc/count/internal/event/strategy/like_strategy.go#37-53
  3. 幂等去重：应用变更前，尝试将 EventID 插入 zfeed_mq_consume_dedup 表。如果 ID 已存在，则跳过事件，避免重复计数。app/rpc/count/internal/event/dispatcher.go#66-74
  4. 事务执行：计数表更新和去重表写入包裹在同一个数据库事务中。app/rpc/count/internal/event/dispatcher.go#65-92

表策略 ​

每类互动都有专门策略，例如 likeStrategy。这些策略负责：

  • 过滤：忽略不影响计数的事件，例如特定 bucket 只追踪内容点赞时，对评论点赞事件进行忽略。app/rpc/count/internal/event/strategy/like_strategy.go#64-78
  • 状态转换：将状态变化（例如 zfeed_like 中的 status: 10 到 status: 20）映射为 delta。app/rpc/count/internal/event/strategy/like_strategy.go#47-50

CountOperator 与原子更新 ​

CountOperator 负责实际修改计数记录。它会根据仓储实现使用乐观版本控制和悲观锁，确保高并发下的正确性。

ApplyDelta 流程 ​

调用 ApplyDeltaWithRepoNoCache 时，它会与 CountValueRepository 交互。app/rpc/count/internal/logic/count_operator.go#65-82

  1. 加锁：仓储使用 SELECT ... FOR UPDATE（clause.Locking{Strength: "UPDATE"}）锁定 (biz_type, target_type, target_id) 元组对应的特定行。app/rpc/count/internal/repositories/count_value_repository.go#159-161
  2. Upsert 逻辑：如果记录不存在，则创建 version: 1 的新行；如果已存在，则递增 value、递增 version，并更新 updated_at 时间戳。app/rpc/count/internal/repositories/count_value_repository.go#166-202
  3. 重试机制：如果出现死锁或锁等待超时，仓储会使用指数退避最多重试 3 次事务。app/rpc/count/internal/repositories/count_value_repository.go#131-144

热度增量分片 ​

除了更新主计数表，写链路还会为热门内容推荐系统提供输入。

权重与分片 ​

  • 权重：不同互动对内容“热度”的贡献不同。点赞加 1 分，评论加 3 分，收藏加 4 分。app/rpc/count/internal/event/dispatcher.go#163-177
  • Redis 分片：为了避免超热门内容造成 Redis hotkey 问题，增量会写入 Redis 中的分片 Hash key。app/rpc/count/internal/event/dispatcher.go#144-152
  • 分片计算：分片由 contentID % HotFeedIncShards 决定。app/rpc/count/internal/event/dispatcher.go#156-161

来源：app/rpc/count/internal/event/dispatcher.go#124-177 app/rpc/count/internal/common/consts/redis/keys.go

缓存失效策略 ​

为了确保读链路（见第 5.2 节）在计数更新后不会返回旧数据，CountOperator 执行双删策略。

  1. 立即失效：数据库事务提交后，立即删除计数对应的 Redis 缓存 key。app/rpc/count/internal/logic/count_operator.go#119-123
  2. 延迟失效：为处理并发读可能从数据库副本读到旧值并重新填充缓存的竞态，会通过 DelayedCacheInvalidator 在短暂延迟（200ms）后调度第二次删除。app/rpc/count/internal/logic/count_operator.go#125-131
