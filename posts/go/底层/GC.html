GC 原理解析 ​

垃圾回收（Garbage Collection）是一种自动内存管理机制，运行时负责找出不再可达的堆对象，并回收它们占用的空间

从运行时实现上看，Go 当前采用的是并发标记-清扫（concurrent mark-and-sweep），辅以三色标记和混合写屏障

常见 GC 算法 ​

在进入 Go 之前，先看几种经典垃圾回收思路

标记-清除 ​

标记-清除分两步：

  1. 从根对象（栈、全局变量、寄存器等）出发，标记所有仍然可达的对象
  2. 清除所有未被标记的对象

优点是对象不需要移动，实现相对直接；缺点是会产生内存碎片。对象被清掉后，堆上可能留下很多不连续的小空洞，这会影响大对象分配

标记-整理 ​

标记-整理在标记之后，会把存活对象向一侧压缩整理，再直接回收整块连续空间。

这样做能明显缓解碎片问题，但对象移动、引用更新、实现复杂度都会更高

半空间复制 ​

复制算法通常把内存划成两块大小相等的区域：

  • from-space
  • to-space

平时只使用 from-space。GC 发生时，把存活对象复制到 to-space，在此过程中顺便完成压缩；一轮结束后再交换两块空间的角色，这样做的好处是分配速度快，不会产生碎片，存活对象会自然变得更紧凑

缺点是要额外预留一半空间

引用计数 ​

引用计数为每个对象维护一个计数器：

  • 对象每多一个引用，计数器加一
  • 对象每少一个引用，计数器减一
  • GC 时将计数器为零的对象删除

回收时机直观；缺点是每次读写引用都要维护计数，开销高，并且解决不了循环引用问题

Golang 中的 GC ​

Go 没有采用 java 的分代 GC，其本身存在逃逸分析机制，会将生命周期较长的对象放入堆中，堆对象也是 GC 的主要对象，不逃逸的对象尽量分配在栈上。而分代 GC 又通常需要额外维护，引入额外复杂度和运行时成本，收益不大。因此 Go 选择了并发标记-清扫 + 混合写屏障 + 栈分配优化这条路线，而不是传统 JVM 风格的分代压缩路线

根集合包括所有 goroutine 的栈、全局变量、runtime 在堆外但仍持有 heap pointer 的内部数据结构

三色标记法 ​

为了让标记过程能够并发执行，Go 使用三色标记来描述对象状态

  • 白色：当前还没被证明存活的对象。GC 结束时仍是白色，就会被回收
  • 灰色：对象本身已被发现存活，但它引用的子对象还没标记完
  • 黑色：对象以及它引用的子对象都已经标记完成

标记的过程，本质上就是一次从根对象出发的图遍历

  1. 标记根对象为黑，把直接所指对象标成灰色
  2. 从工作队列中取出灰色对象，标记它引用的子对象为灰色。当其所有对象处理完后，再把自身标记成黑色
  3. 重复以上过程，到最后剩下的白色对象就是不可达对象

并发标记带来的问题 ​

Go 在 1.5 版本之后引入了并发垃圾回收机制。Go 的并发垃圾回收中 GC 是与业务代码并发执行，所以代码可能会在标记期间继续修改对象引用关系。这就带来了两个典型问题

  1. 漏标

漏标是正确性问题，后果最严重。对象明明还活着，但 GC 没有标到，最终把它当垃圾回收掉了

典型触发条件有两个，而且通常需要同时满足：

  1. 黑色对象指向了白色对象
  2. 原本能到达该白色对象的灰色引用链又被删掉了

一旦这两个条件同时成立，这个白色对象就可能从 GC 的视角里消失

  1. 多标

多标是空间效率问题。某个对象本来已经死了但因为 GC 采取了保守策略，仍然把它保留下来了，这类对象通常被称为浮动垃圾。它们不会在本轮被回收，只能等下一轮

强弱三色不等式 ​

漏标问题本质上是一个已经被扫描完的黑色对象指向了一个被灰/白色对象删除引用的白色对象

  1. 黑色对象指向白色对象
  2. 灰/白对象删除了白色对象
  3. 1 2 步中的白色对象是同一个对象
  4. 1 发生在 2 之前

强弱三色不变式就是用来解决漏标问题的

  • 强三色不变式：不管有没有灰色对象保护，黑色对象一律不允许直接引用白色对象。即杜绝条件1
  • 弱三色不变式：黑色对象可以引用白色对象，但需要某个灰色对象出发仍然可以到达该对象

插入写屏障 ​

  • 当一个黑色对象 A 想要引用一个白色对象 B 时，屏障触发，强制把 B 改为灰色。A 指向了灰色对象，满足了强三色不变式

删除写屏障 ​

  • 当一个灰色对象 A 想要删除对一个白色对象 B 的引用时，屏障触发，强行将 B 标记为灰色，保证的是弱三色不变式

混合写屏障 ​

屏障机制涉及频繁的轻量操作，为了避免开销过大，屏障机制无法作用于栈对象，单一的屏障机制无法真正解决漏标问题，所以 Go 又引入了混合写屏障

  • GC 开始前以栈为单位分批扫描，将栈中所有对象标记为黑
  • GC 期间栈上新创建的对象直接标记为黑
  • 堆对象正常开始插入/删除写屏障

几种例子：

  1. 堆对象删除引用，栈对象建立引用

堆上的白色对象 B 建立对堆上白色对象 C 的引用，栈上的黑色对象 A 尝试对 C 建立引用，因为栈上没有屏障机制，成功建立引用，而当 B 尝试删除对 C 的引用时，因为删除写屏障触发导致 C 被标记为灰色，因此不会漏标

  1. 一个堆对象删除引用，成为另一个堆对象下游

堆上白色对象 A 引用了堆上白色对象 C，堆上黑色对象 B 尝试对 C 建立引用，因为插入写屏障触发，C 被标记为灰色，A 删除对 C 的引用，而 C 已经变成灰色，没有漏标

  1. 栈对象删除引用，成为堆对象下游

栈上白色对象 A 引用堆上对象 C，堆上黑色对象 B 尝试建立对 C 的引用，这时插入写屏障触发，导致 C 被标记为灰色，A 删除对 C 的引用也不会漏标

  1. 一个栈对象删除引用，另一个栈对象建立引用

栈上白色对象 A 引用堆上白色对象 C，栈上黑色对象 B 建立了对 C 的引用，A 删除对 C 的引用。 这种场景下，C 要么已经被标记为灰，要么从某个灰对象触发仍然可达 C。因为这个例子中，对象B能建立指向C的引用，至少需要满足如下三个条件之一：

  • 栈对象B原先就持有C的引用，如若如此，C就必然已处于置灰状态（因为B已是黑色）
  • 栈对象B持有A的引用，通过A间接找到C，然而这也是不可能的，因为倘若A能同时被另一个栈上的B引用到，那样A必然会升级到堆中，不再满足作为一个栈对象的前提
  • B同栈内存在其他对象X可达C，此时从X出发，必然存在一个灰色对象，从其出发存在可达C的路线
